# dsh-pdf-studio

DSH 的 PDF 工作台：**逐页分诊 → 按类型处理 → 可编辑/可搜索输出**。
同时支持 **web GUI 与桌面端**。

一期已落地并验证的能力：

- **分诊**：逐页判定 `text` / `image` / `mixed` / `empty`，并给出判据
- **文本型**：直接读 pdf.js 文本层，**精确、不 OCR**
- **图片型**：tesseract OCR，取**行级坐标**，换算回 PDF 坐标
- **可搜索 PDF**：保留原扫描图，叠加**隐形文字层**（`3 Tr`），中文可搜

---

## 为什么是 host-only 架构

界面**不是** `dsh.client` 客户端插件，而是由宿主自己的路由提供、注入进页面的普通脚本。

原因是踩过的坑：`dsh.client` 插件要通过 GUI 的客户端模块系统物化，而它声明的 `dsh.client.inject`
要对着**当前运行的那个外壳**的服务图解析。桌面端外壳的服务图和 web 外壳不是同一套 ——
声明了对方没有的服务，插件就会永远停在 `pending (waiting for service)`，功能不出现且不报错。

所以本插件只做宿主侧，浏览器侧是自带的静态脚本，经**两条通道**注入：

| 通道 | 适用外壳 | 说明 |
|---|---|---|
| `webServer.tapIndex` | web | 直接改写 `index.html` |
| `webserver/index-inject` | 桌面 | 结构化行表交给渲染层追加 |

两条都注册，各自在不适用的外壳上是空操作。

### ⚠️ 注册顺序陷阱

桌面端宿主的注入表是**启动时一次性收集并缓存**的，没有刷新路径。插件的
`webserver/index-inject` 监听如果晚于那次收集，行就永远进不去，而且**没有任何报错**。

因此 `apply()` 的**第一条语句**就挂上监听；所有依赖服务的动作放进
`root.inject([...], cb)` 里等待。见 `src/index.ts`。

## 分诊为什么要三条判据

"文字层非空就是数字版"是错的，而且错得很贵。

实测 `demo/source/ceshi.pdf`（6 页扫描件）：**每页都有文字层**，但内容只有一串
防伪指纹 `{#{QQAB…=}#}`，位于 `y=0`、5pt 字号，正文一个字都没有。只看"有没有文字"
会把整份扫描件判成数字版，然后给用户一个空的编辑器。

所以三条一起判：

| 判据 | 作用 |
|---|---|
| 可信字符数 | 排除只有零星字符的页 |
| **位置与字号** | 页边 24pt 带内、≤7pt 的字符视为指纹/水印，不计入正文 |
| 图像覆盖 | 有整页图像 → 扫描件 |

实测判定：`ceshi.pdf` 6/6 → **图片型**（正文占比 0%）；`contract.pdf` → **文本型**（260/260，100%）。

## 依赖库的坑（都已付过代价）

这些**都是静默失败**，所以记在 `contracts.ts` 里：

1. **`pdf-lib@1.17.1` 的 `drawText()` 没有 `renderingMode` 选项** —— 传了会被忽略，
   隐形层会变成**盖在扫描件上的可见黑字**。必须手写算子
   （`page.pushOperators(...setTextRenderingMode(3))`）。
2. **`pdfjs-dist@6.2.108` 没有 `doc.destroy()`** —— teardown 走
   `loadingTask.destroy()`。`destroy?.()` 会静默变成空操作、泄漏 worker。
   `openPdf` 已把它统一成 `PdfDoc.dispose()`。
3. **`tesseract.js` 在 Node 下必须用 node 版 worker**，否则
   `r.g.addEventListener is not a function`；且 **`blocks` 默认 `false`** ——
   不开就没有任何坐标。
4. **`fontkit@2.x` 与 `pdf-lib@1.17.1` 不兼容**（`encodeStream()`→`encode()`），
   且 macOS 中文字体**全是 `.ttc`**，`fontkit.create()` 返回的是集合而非字体。
   已在模块内做适配。
5. **字体资源键是按页声明的**。按"字体"缓存会让第二页的 `/Font` 字典为空 ——
   文字照常渲染，但提取出来是裸字形码，于是"可搜索 PDF"其实搜不到。
6. **pdf.js 的文本 transform 已经是 PDF 坐标，不要翻转** ——
   全页 13 项实测：按 PDF 解读命中 397 墨点，按设备坐标解读命中 0。

## 可编辑模型：可读的 run（已打通）

画板要显示的不是字形 ID，而是文字。所以补上了 **ToUnicode 解码**这一层：

| 能力 | 说明 |
|---|---|
| `parseToUnicodeCMap` | 解析 CMap 的 `bfchar` / `bfrange`（含数组式与递增式两种）与 codespace 宽度 |
| `readPageFonts` | 逐字体读取 `ToUnicode`、`/W` 宽度表、`/DW` 默认宽度 |
| `listReadableRuns` | 给出每个 run 的 `id` / **解码文本** / 字体 / 字号 / 基线 / **实测宽度** |
| `readEditableDocument` | 整份文档的可编辑模型（按页组织） |
| `applyTextEdits` | 按同一个 `id` 回写，并**另存新文件**（永不覆盖源） |

真实合同上解码结果（13 个 run 全部可读）：

```
1:6   y=762 size=22 w=106.3pt  "服 务 合 同"
1:16  y=782 size=10 w= 50.0pt  "合同编号："
1:26  y=692 size=11 w=176.0pt  "甲方（委托方）：示例科技有限公司"
1:76  y=560 size=11 w=385.0pt  "四、保密条款：双方对本合同内容负有保密义务，未经对方书面同意不得披露。"
3:6   y=120 size=12 w=228.0pt  "【法务终审】条款审核通过，同意盖章签署"
```

**解码正确性是交叉验证过的**：把整页解码出的字符与 pdf.js 的提取结果逐字符比对 ——
**134 个不同字符完全一致、总数 260/260 一致**。这比抽查某个 run 有力得多，因为
CMap 用错时通常只影响页面上的一部分字体。

**读-改-读 闭环已验证**：

```
读模型 → 取到 run 1:76「四、保密条款…」→ 按该 id 改写 → 重新读取输出
  → 该 run 变为「四、保密条款：…（已由法务修订）。」
  → 其余 12 个 run 文本完全不变
```

（改写后 id 会变，因为新嵌入的子集让算子下标整体前移 —— 这是正确行为，见下方"已知边界"。）

### 溢出预警

替换后用**各自字体的度量**测量宽度并预警，而不是看字符个数 —— 替换字体与原字体的
advance width 通常不同。实测：

```
短替换  → 无提示
超长替换 → "3:6 替换后预计宽约 576.0pt（估算），超过原 228.0pt，可能向右溢出"
```

### 内容流回写：已打通（实测）

**改字是可行的，而且是外科手术式的。** 在真实合同上把页脚文字替换掉，验证结果：

| 检验 | 结果 |
|---|---|
| 替换后的文字可被提取 | ✅ 重新打开 PDF 能读到新文本 |
| 原文字消失 | ✅ 旧页脚文本不再出现 |
| 页面其余部分仍正确 | ✅ 标题、编号、正文全部完好 |
| **未改动的内容流逐字节相同** | ✅ 3/3 个流字节级一致 |
| **改动仅限目标算子窗口** | ✅ 窗口前的 head、窗口后的 tail 完全未动 |
| **渲染像素差分** | ✅ 变化全部落在被改文本块内；该块上方**0 个像素变化** |
| 新字体子集已登记 | ✅ `/Resources /Font` 多出 `ArialUnicodeMS` |
| 源文件未被修改 | ✅ SHA256 全程不变 |

编辑后的内容流（对比原文，只动了这一处）：

```
原文: /ArialUnicodeMS-6703682664 12 Tf ... 1 0 0 1 70 120 Tm <0001...0012> Tj
改后: /ArialUnicodeMS 12 Tf <000100020003000400050006000700080009> Tj
      1 0 0 1 70 120 Tm 保持不动 → 基线完全不变
```

**实现要点**（每一条都是踩出来的）：

1. **把整个文本状态窗口当一个 span 替换** —— 从 `Tf` 的字体操作数到最后一个字形串。
   拆成"字体名"和"字形"两个 span 会失败：字体名那个 span 一旦丢失，流就会
   **用旧字体显示新子集的字形 ID**，文字画成乱码、提取为空。
2. **`Tf` 是独立算子**，不在 `Tj` 的操作数里 —— 必须向前扫描找到生效的那一个。
3. **窗口天然包含结尾的 `Tj`** —— 替换文本不能再自带 `Tj`，否则得到 `...> Tj Tj`。
4. **pdf-lib 的 `encodeText()` 返回 `PDFHexString`**，不是 Buffer —— 用 `.length`
   或下标去读会得到 `undefined`，看起来像"没实现"（我为此白查了一轮）。
5. **`/Contents` 是数组时必须换引用，不能改内部** —— 用 `PDFRawStream.of` +
   `context.register` 登记新流，再重建 `/Contents` 数组。

### 内容流回写的关键约束（实测）

1. **页面是多个内容流组成的数组**。`contract.pdf` 的 `/Contents` 有 4 个流
   （`q` / 正文 / `Q` / 尾段），13 个 showText 分布在流 1 与流 3 —— 补丁必须定址到正确的流。
2. **文本是字形 ID，不是字符**。`<0001000200030002000400020005>` 是该字体子集里的
   字形序号；字符含义由字体的 `ToUnicode` CMap 决定。所以解析器**返回原始操作数**，
   绝不假装能解码成字符串。
3. **字体键是按页、且每段文本一个子集**。该页 13 个字体资源全部是同一底座的独立子集，
   **且全部指向同一个 PDF 对象**。改字若要新字形，最稳的做法是**新嵌入一个子集**并
   在资源字典里登记，而不是去改原字体。
4. **pdf-lib 的字形编码只在保存期可用**。`CustomFontSubsetEmbedder.encodeText()` 依赖
   `subset.includeGlyph()` 分配**子集内**的 ID，而 `subset` 在 `embedFont` 之后、保存之前
   并不就绪 —— 直接调用返回空。因此内容流拼接必须放进**保存钩子**里执行，不能提前算好。
5. **无损性是补丁可信的前提**。解析器保证"把 token 拼回去等于原文"，实测 4/4 个真实流
   完全无损；这样"只有目标 span 变化"才是可检验的性质。

### 已修复的真实缺陷（解析器）

分词器早期在遇到**转义括号**时会让扫描位置越过输入末尾（`i += 2` 无边界检查），
外层数组扫描随之失去终止条件，**无限循环并耗尽内存**。已重写为每个分支都保证前进，
并加了 10 个畸形输入（未闭合字符串/字典/数组、游离分隔符、末尾反斜杠）的终止性回归测试。

## 画板：可点选、可改字、可另存（已打通）

浮层现在有两个标签页：**分析**（分诊 + 可搜索 PDF）与**编辑**（画板）。

做法：**宿主把页面栅格化成 PNG 做底图**，浏览器侧按每个 run 的 PDF 几何叠加
可点选框。渲染刻意放在宿主侧 —— 浏览器侧就不必配置 pdf.js worker，少一个
环境相关的失败点，并且复用了 OCR 阶段已经验证过的渲染路径。

| 交互 | 行为 |
|---|---|
| 点框 | 选中并打开编辑器，显示 run id / 字体 / 字号 / 基线 / 实测宽度 |
| 改字 → 应用 | 框变绿，底部列出待写改动，可逐条撤销 |
| 另存编辑结果 | 调 `/apply` 写新文件（**永不覆盖源**），返回应用处数与提示 |
| 翻页 / 缩放 | 逐页浏览，滑块缩放；底图按页缓存，不因改字重新拉取 |

### 为什么这块值得测：y 轴翻转

PDF 是**左下原点**，底图是**左上原点**，每个框都要翻转一次：

```
top = (pageHeight - (run.y + height)) * scale
```

符号写反会把所有框**上下镜像** —— 在对称页面上看着正常，在其他任何页面都是错的。
所以测试用 run 自身的真实几何**独立算出期望坐标**再比对，并额外加了一条性质断言：
"高处的 run 必须显示在低处 run 之上"。

实测（`contract.pdf`，底图宽 595px）：

```
标题 run (PDF y=762)  → top =  52.5   期望 52.5
页脚 run (PDF y=120)  → top = 706.6   期望 706.6
且 52 < 707  → 翻转方向正确
```

### UI 是怎么验证的

`public/app.js` 是无依赖、由注入加载的普通脚本，所以测试**真的把它跑起来**：
jsdom 建文档 → 执行该脚本 → 打桩 `fetch` → 走完「选文件 → 载入可编辑内容 →
点框 → 改字 → 另存」，并断言最终 POST 的载荷（目标 run id、新文本、页码）。

这顺带抓到一个**真实体验缺陷**：原先每次改字都重建底图并重读 `clientWidth`，
叠加层会瞬间塌陷、画面跳动。已改为按页缓存底图。

## 密码保护：加密 / 解密（已打通）

加密**没有自己实现** —— 而是交给 **qpdf 编译成的纯 WASM**（`@jspawn/qpdf-wasm`，
Apache-2.0，零依赖）。密钥派生、owner/user 权限分离、revision 6 哈希都是专业活，
自己写一个"看起来能开"的版本，结果往往是别处打不开、或比宣称的更弱。

| 能力 | API |
|---|---|
| 加密（用户密码 + 所有者密码 + 权限） | `encryptPdf` |
| 解密（凭密码） | `decryptPdf` |
| 查询保护状态 | `inspectEncryption` |
| 端到端（读文件 → 写文件，**不覆盖源**） | `protectPdf` |

实测闭环（`contract.pdf`，AES-256）：

```
原文        → encrypted=false  opens=true
加密后      → encrypted=true   opens=false      ← 独立读取器拒绝提取文字
错误密码    → 拒绝（exit 2）
空密码      → 拒绝
正确密码    → 解密成功 → encrypted=false opens=true
            → pdf.js（独立实现）能读、页码保留、正文完好
```

### 让 qpdf 在 Node 里跑起来

qpdf-wasm 是 Emscripten 浏览器构建：模块作用域就读 `self`/`document`，加载 `.wasm`
走 `fetch`（无法解析裸文件路径），还依赖 `Worker`。解法不是堆 polyfill，而是
**自己编译 wasm 再通过 Emscripten 的 `instantiateWasm` 钩子交进去** ——
模块自带的加载器完全不执行，全程只用本地字节。

### 三个必须记下的"静默错误"

1. **不能从 qpdf 日志判断加密状态。** `--show-encryption` 的报告**走不进**
   Emscripten 的 `print`/`printErr` 钩子（`output` 是空串），基于日志的判断会把
   **已加密的文件报成未加密** —— 对这个功能而言是最坏的失败方向。因此改为结构化判定：
   `/Encrypt` 取自 **trailer**（不是全文搜索，否则正文里的 `/Encrypt` 字样会误报），
   "能否免密打开"由一次真实的零密码读取决定。
2. **`--modify` 只接受一个值。** 逗号列表会被直接拒绝；而权限层级是累积的
   （`form` 已含批注、`assembly` 已含表单），所以多个请求必须**收敛到最高那一级**，
   不能拼接 —— 拼接是最自然的写法，且每次都失败。另外值名是 `assembly` 不是 `assemble`。
3. **模块会污染 `process.exitCode`**（实测被设成 2）。在 CLI 里这是预期行为，
   在长期运行的 DSH 宿主里就是污染 —— 会让整个进程无端以非零码退出。
   已保存/恢复原值。

第 3 条顺带牵出我自己的一个 bug：我一开始把 `process.stdout.write` 换成"吞掉字节"的
函数，**破坏了 Node 自身的错误输出通道**，于是任何 teardown 异常都变成"静默 exit 2、
没有任何信息"，排查了很久。现在改为**观察并转发**（原始 write 照常执行），
`process.stdout` 在 Node 26 上也已不可赋值。

## 水印：加得可靠，删得诚实（已打通）

### 加水印

水印被写成**一个 Form XObject，每页用一条 `Do` 调用**，并在 XObject 的 `/Name`
里写入身份标识。这是三重收益：文件更小；水印的图形状态**天然被隔离**
（XObject 自带 `q`/`Q` 作用域）；以及最重要的 —— **之后的删除有唯一一个算子可删，
而不是要猜一个图案**。这是设计选择，不是巧合。

支持 `tile`（斜向平铺）/ `center` / `corner` 三种位置、旋转、透明度、颜色、字号、
图片水印，以及按页选择。

### 删水印：能删到什么程度，取决于它当初怎么被写进去

| 写入方式 | 能否删除 | 原因 |
|---|---|---|
| 页面用 `Do` 调用的 Form XObject | ✅ 精确删除 | 调用就是一个算子，删掉它即删掉整块，且不碰其他内容 |
| 内联在页面流里的算子 | ⚠️ 通常可以，但属启发式 | 它与正文在种类上无法区分，只能靠几何与图形状态判断 |
| 栅格化进页面图片 | ❌ 不能 | 像素就是页面本身，分离它们是图像修复，必然有损 |
| 作者当正文画的 | ❌ 不能 | 那就是正文 |

所以 `scanWatermarks` 返回**带置信度和理由**的候选，`removeWatermarks` 默认
**只删能自证的**（置信度 ≥ 0.9），并且**默认 dry run**。它从不宣称"什么水印都能删"——
那个宣称是假的，而一个"静默删掉一半"的工具比一个"说清为什么不能删"的工具更糟。
无法处理的情况会出现在 `refused` 里，UI 会把它显示出来，避免"空列表"被误读成"这个文件很干净"。

### 实测（真实合同）

```
source sha       : 34663ac69c12
watermarked sha  : ea2c15d5fbbf  | differs: true
scan watermarked : 1 candidate(s)   ← 置信度 100%，按 /Name 识别
cleaned scan     : 0 candidate(s)
渲染像素差分     : 移除后 0 个像素与原文不同  ← 完全还原
正文可提取       : 是（服务合同…）
源文件           : UNCHANGED
```

### 添加水印时踩到的两个坑（都会导致"水印隐形"）

1. **必须写字体编码后的字形串，不能写原文字。** 子集字体会重新编号字形，
   直接写 `(内部资料) Tj` 画出来的是"恰好落在那些码位上的字形"，也就是乱码或空白。
   必须用 `font.encodeText(text)` 的结果作为操作数。
2. **XObject 的 `/Resources` 必须指向真实对象。** 我一开始写成空字典占位
   （`{ [fontRef]: {} }`），于是 `Do`/`Tf` 解析到空对象，**整个水印画出来是空的** ——
   文件里结构齐全、扫描器也认得，但页面上什么都没有。这个坑只有渲染出来看才能发现，
   所以"渲染像素差分"是这套测试里最有价值的一条。

## 浮层可以拖到屏幕任意位置（已打通）

工作台浮层和右下角按钮都**可拖动**，并且**记住位置**：

| 操作 | 行为 |
|---|---|
| 拖标题栏 / 拖浮层头部空白处 | 移动浮层到任意位置 |
| 拖右下角按钮 | 移动按钮本身 |
| **双击标题栏（或按钮）** | 一键复位到默认右下角 |
| 关闭再打开 / 刷新页面 | 回到你上次放的位置 |

### 两个必须处理的细节

1. **位置要裁剪在视口内。** 存了绝对坐标却不裁剪，窗口一旦变小，浮层就永久跑到屏幕外——
   除了清站点存储没有别的办法弄回来。所以在**加载时和每次 resize 时**都会裁剪，
   保证至少 72×32px 留在可见区域内。
2. **按钮既能拖、又能点开浮层，两者必须区分。** 用移动距离阈值（3px）+ 捕获阶段
   的 click 抑制：拖动不会顺带把浮层弹出来，纯点击照常打开。这条如果做错，
   *每次想挪动按钮都会弹出浮层*，功能会显得完全坏掉。

### 排除规则踩的坑

我第一版把"排除按钮"写成 `event.target.closest('button, input, select, .tab')` ——
但**浮动按钮自己就是 `<button>`**，于是匹配到自身、直接 return，按钮根本拖不动。
测试立刻抓到了。正确写法是先判断 `event.target !== handle`，只排除**手柄内部的**控件。
（浮层头部同时是拖拽手柄，所以这条判断对两处都必要。）

### 实测（jsdom 里跑真实脚本）

jsdom 的 `getBoundingClientRect()` 返回全 0，这让拖拽数学变成**确定性的**：
抓取偏移就等于指针位置，所以指针移到 (clientX, clientY) 后，浮层应精确落在差值处。

```
拖头部 (100,100) → (160,140)  =>  left=60px top=40px      ✓ 精确等于差值
right/bottom 锚定切换为 auto                              ✓
位置写入 localStorage                                      ✓
拖出边界 (99999,99999)        =>  裁剪到 952px (=1024-72)  ✓ 仍在可抓取范围
双击标题                       =>  复位到 right:18px，并清除存储  ✓
拖按钮                         =>  浮层未被打开            ✓ 点击被抑制
纯点击按钮                     =>  浮层打开                ✓
```

## 交互模型：Agent 工具（现在的主动面）

**浮层面板已经移除。** 之前那版是"先把面板摆在你眼前、再让你填表"——那是把一个桌面应用
硬塞进对话界面，插件在你还没有任何结果时就索取注意力。现在改成最初需求描述的那种交互：

> 用自然语言说要做什么 → Agent 调用工具 → 结果回到会话里

注册了 **6 个工具**：

| 工具 | 作用 |
|---|---|
| `pdf_inspect` | 页数 / 尺寸 / 是否加密 / 按页类型；可选列出可编辑文字块（含 id） |
| `pdf_extract_text` | 提取文字与行坐标（文字层或 OCR） |
| `pdf_make_searchable` | 扫描件 → 可搜索 PDF（不可见文字层，外观不变） |
| `pdf_edit_text` | 按 id 替换现有文字，位置与其余内容不变 |
| `pdf_watermark` | `add` / `scan` / `remove` 三合一 |
| `pdf_protect` | `check` / `encrypt` / `decrypt` |

### 设计规则

- **破坏性操作永不覆盖源文件。** 每个产出文件的工具都接受可选 `output`，默认写到源文件旁的
  新文件；显式指定源文件本身会被拒绝（有测试覆盖）。这条保证是 Agent 可以无人值守调用它们的前提。
- **昂贵操作必须显式开启。** `pdf_inspect` 默认只读几何信息（约 10ms）；完整分诊要 `analyze=true`，
  因为扫描件的 OCR 是每页数秒级——静默花掉三十秒比先问一句更糟。
- **模棱两可要报告，不要猜。** 判断不了的水印带着置信度和理由返回，并保持原样不动。

### 会话内预览（不需要客户端插件）

竞品那种"实时预览窗口"我原以为要写客户端插件。查了它的源码后发现**不用**：

```js
// dsh-univer-office 的 screenshotTool
render: (_args, value) => [
  { type: "text", text: JSON.stringify(value) },
  ...value.result.images.map(item => ({ type: "image", attachment: imageRef(item.image) })),
]
```

**图片作为 `{type:"image", attachment:ref}` 内容块返回，由内置的图片卡片渲染。**
所以 `pdf_preview` 工具就能把页面渲染成图片直接显示在会话里，零客户端风险。

### 一个会让工具完全无法运行的坑

宿主用 `assertRenderedContent` 校验 `output.render` 的返回值：

```js
✓ return [{ type: 'text', text: String(value) }]   // 必须是内容块数组
```

我一开始返回的是 `{ content: [...] }` —— **类型上说得通、我自己的测试也全绿，但真正被调用时会立刻抛错**。
因为我的测试断言的正是我自己编错的约定。现在改成数组，并加了一条针对该约定的断言。

### 一个实现上的坑

工具对象是**本模块自己构造**的，不是用 `defineTool` 生成的。

原因：`@deepseek-ai/dsh-tools` 能从 **profile** 解析，但**不能从本插件的真实路径解析** ——
插件是用 `link:` 安装的，Node 会把软链解析到真实路径，于是 bundle 里那句
`import('@deepseek-ai/dsh-tools')` 会抛 `MODULE_NOT_FOUND`，尽管 profile 明明能解析它。
依赖它就意味着要自带一份宿主包的副本并祈祷版本一致。

所以我读出了 `defineTool` **实际产出的对象结构**（`{name, description, parameters, output:{schema,render}, execute, presentCall}`），
自己构造，并自带一个小 schema 编译器（约 40 行）把参数规范编译成 JSON Schema。
顺带自己做了参数校验，好让模型的非法调用得到可读报错。

过程中发现 schema 子集的两条硬规则：**`additionalProperties` 必须是显式布尔值**（嵌套对象上），
而**值 schema 不接受 `required`**。这两个都是撞了报错才知道的。

### 顺带修掉一个真 bug

`inspectDocument` 少了 `ignoreEncryption`，导致**检查加密文件时直接抛异常**——
而"这个文件加密了吗"恰恰是调用方最需要答案的场景。现在能正确报告已加密。

## 预览：打开就能看到文档（已打通）

浮层第一个标签页就是**预览**。选好文件点「打开预览」，所有页面以缩略图铺开，
点任意一页放大到全屏。

| 细节 | 做法与原因 |
|---|---|
| 页面几何从 `/info` 取，**不走** `/analyze` | 分析会对扫描件跑 OCR（每页数秒）。为了看第 1 页而等 OCR 是不可接受的。`/info` 只读页面尺寸，扫描件 6 页 **10ms** |
| 缩略图 `loading="lazy"` | 200 页的文档只加载滚动到的那些页 |
| 缩略图尺寸自适应 | 按页面 pt 宽 × 目标 CSS 宽算缩放比，不是写死倍数 |

### 这里修掉两个真 bug

**① 懒加载与 `display:none` 死锁（就是它导致你只看到"第 1 页"）**

第一版我这样写：

```js
img.loading = 'lazy'
img.style.display = 'none'          // 加载完成前隐藏
img.addEventListener('load', reveal) // 加载后显示
```

这是一个**死锁**：`display:none` 的图片没有布局盒 → 浏览器认为它永远不在视口内 →
**永远不发起请求** → `load` 永不触发 → 永远保持隐藏。用户看到的是一格格
"第 N 页"占位符，而不是文档。

修法：图片**始终参与布局并可见**，占位符作为**绝对定位的浮层盖在它上面**，
加载完成后移除占位符。图片再也不会被隐藏。

之所以没被测试抓到：**jsdom 不实现懒加载**，`img.src` 设上就是设上，`complete` 逻辑
根本不起作用。现在补了一条直接针对该条件的断言：**缩略图不得为 `display:none`**。
我把旧代码改回去验证过，这条断言会 FAIL。

**② 状态行被覆盖**

`renderPages` 会把"N / M 页已显示，K 页失败"写进状态行，但调用方在它之后又写了
一次，把计数冲掉了。改成先写摘要、再渲染。

### 这里修掉一个真 bug

我第一版把 `<img>` 先建好、**加载完成才插入 DOM**。看起来没问题，实际上
**`loading="lazy"` 完全失效** —— 浏览器只观察文档里的元素，游离的 `<img>` 根本不被观察，
于是长文档会一次性拉取所有页。现在图片立即入 DOM 并先隐藏，加载完成后显示，
懒加载才真正生效。

### 顺带修好渲染保真度

预览要**渲染**页面，这让一个之前的判断过期了。`src/core/pdf.ts` 里原本写着：

> 缺少标准字体只影响渲染保真度，绝不影响本管线读取的文本层

在只做文本抽取时这是对的；但预览和画板现在都要渲染，字体缺失是**看得见**的。
于是接上了 pdfjs 自带的两套资源：

- `standard_fonts` —— 未内嵌的 14 种标准字体
- `cmaps` —— 预定义 CJK 编码（中文文档尤其相关）

实测非内嵌 Helvetica 的渲染：字节 11520 → 12526、深色像素 3661 → 3728，
且 pdf.js 的 `standardFontDataUrl` 警告**从 2 条降到 0 条**。

找这两个目录时我先写错了层级（`standard_fonts` 在包根目录，而入口嵌在下面两层），
导致指向一个不存在的路径且**静默无效**。现在改成从入口向上逐级查找。

### 已知边界





- **改写后 run 的 id 会整体前移**（例：`1:76` → `1:74`）。id 是"流下标:算子下标"，
  而插入新字体资源会让后续算子下标变化。因此**一次编辑要用同一份模型里的 id**，
  跨编辑不要缓存 id —— 每次改完重新读模型。
- 溢出预警是**估算**：新嵌入的子集在写盘前没有自己的 `/W`，按字体默认宽度计。
  提示文案里已标明"估算"。
- 尚未处理：跨 run 的整段重排、字距微调（`TJ` 的数值调整）、自动换行。
