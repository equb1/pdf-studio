## 按功能详解

下面按类别逐个给出参数、默认值、真机实测结论与已知坑。

## 文字与内容改写
### 注释标注（`pdf_annotate`）

批改、圈重点、盖"已阅"——写进 PDF 的**注释层**，而不是画进页面内容：这样在阅读器里能选中、
编辑、删除、导出，语义上就是"批注"。

| action | 目标定位 | PDF 子类型 | 默认颜色 |
|---|---|---|---|
| `highlight` / `underline` / `strikeout` | `find="要标注的文字"`（在该页文字层里定位） | `/Highlight` `/Underline` `/StrikeOut` | 高亮黄 `#ffd400`、下划线/删除线红 `#e53935` |
| `box` / `ellipse` | `rect={x,y,width,height}` | `/Square` `/Circle` | `#e53935` |
| `freetext` / `note` / `stamp` | `rect` + `contents` | `/FreeText` `/Text` `/Stamp` | 黑 / `#ffd400` / 蓝 `#1565c0` |

要点与坑（都已在真机验证）：

- **每个注释都写 `/F 4`（Print 标志）**。没有它，注释在打印与打印预览里不会出现——这是
  "批改完打印出来发现批注没了"的根因。
- **文本标记与方框/椭圆必须带 `/AP` 外观流**。PDF 规范允许这类注释不带 `/AP`、由阅读器按
  `/QuadPoints` 自己画，Acrobat 确实会——但 **macOS 的 PDFKit（预览/QuickLook）不会**：
  实测不带 `/AP` 时高亮渲染出来**像素差异为 0**（等于看不见）。所以这里一律显式给外观。
- 文本标记的几何是**按字符占比在整行宽度内插值**的近似（中英混排不是等宽字体，误差远小于一个字宽）；
  **跨行匹配只取第一行**。要精确到某个文字块，请用 `pdf_edit_text` / `pdf_replace_line`。
- `find` 定位依赖**文字层**：扫描件（整页图片）没有文字层，会明确报错并提示先 `pdf_make_searchable`。
- 注释外观由阅读器渲染；我们的 `pdf_preview` 走 pdf.js 的 canvas，**可能不显示注释层**——
  请在系统预览 / Acrobat 里确认观感。
- `pdf_inspect` 现在会报注释数量与子类型（例如 `注释：1 个（Stamp ×1）`）。

### 页面写字（`pdf_text`）

页码、页眉页脚、Bates 编号、随手插一行字——四件事落到 PDF 上都是"**在页面某个位置用嵌入字体画字**"，
所以归一个工具，四个 action：

| action | 写什么 | 默认落点 | 可用占位符 |
|---|---|---|---|
| `insert` | `text`（可含 `\n` 换行） | `center`（给 `rect={x,y}` 就固定在那个位置） | `{page}` `{total}` `{date}` `{filename}` |
| `page-number` | 默认 `{page} / {total}`，可用 `text` 换模板 | `bottom-center` | 同上 |
| `header-footer` | `header` / `footer` 两个模板（可只给一个） | 顶部 / 底部居中 | 同上 |
| `bates` | `prefix` + 补零序号 + `suffix` | `bottom-right` | 无（用 `start`/`digits`） |

要点：

- **写在内容流里，不是注释层**：因此**可搜索、打印会出现、也能被后续改写**（`pdf_edit_text` / `pdf_replace_line`）。
  这与 `pdf_annotate` 的"批注"语义是刻意区分的——页码/页眉属于文档内容，不该混进批注列表。
- **`{page}` 是"显示的页码"**：从 `start` 开始、按**选中顺序**递增（只选第 3 页且 `start=10` → 显示 10）；
  全文档编号时 `start=1`，等于真实页号。`bates` 的序号同样按选中顺序递增。
- **未知占位符不静默吞掉**：`{pages}` 这种拼错的占位符会**原样写进页面**，并在结果与确认单里明确提示，
  而不是被替换成空串让人以为写对了。
- **中文自动嵌入系统字体**（含中文才嵌 CJK，纯 ASCII 走内置 Helvetica，省体积）。
- `pages` 支持 `1-3,7` 与 `odd` / `even`；越界或倒序范围给中文错误。

### 整行重绘（改长一个词怎么办）

`pdf_edit_text` 只把指定文字块的字形串换掉、**不移动后面的文字**，而 PDF 没有"段落"概念，
所以把一个词改长（`turn` → `turning`）会直接压在后一个字上——引擎只能提示"可能向右溢出"，
不会阻止。`pdf_replace_line` 就是为这件事准备的：

1. 先用 `pdf_inspect runs=true` 拿到**目标行里任意一个**文字块的 id；
2. 调一次
   `pdf_replace_line path=<路径> page=<页码> targetId=<id> text="<这一整组的新文字>" output=<输出>.pdf`；
3. 插件会定位该文字块所在的 `BT … ET` 绘制组，把组内字形串**抹掉**（是真的删掉，不是盖一层），
   再用真实几何算出的页面坐标原点与页面字号把新文字**重画**上去，长度自由；若新文字变长，
   还会把**同一视觉行右侧的兄弟绘制组整体右移**同样的距离（跨组重排，见下）。

要点：

- **它抹的是整组，不是"那一句"。** 若这一组不只有你要改的内容，请改用 `pdf_edit_text`
  （它只换字形、不整组重绘），或者把整组文字都写进 `text`。工具描述与结果里的 `注意：` 都会提醒。
- **默认会做跨组重排（`shiftSiblings: true`）。** 真实文档（包括那份 73 页 WPS 导出）常把视觉上的
  一整行拆成多个 `BT … ET` 组：`9.turn` 一组、`around/round` 一组、`转身` 一组。新文字变长时，
  这些右侧组会**各自按同样的 Δ 整体右移**：每个组由自己的绝对 `Tm` 锚定，所以只改那个 `Tm` 的
  平移分量，组内相对位移自动跟随（这正是"改相对位移链上的一个点会搬错字"的反面）。
  结果里会写明 `已把同一视觉行右侧 N 个片段整体右移 X.XXpt`。
  - 传 `shiftSiblings: false` 就不动版面，此时若新文字越过右侧组，会给出重叠警告，而不是假装没事。
  - 组的第一个定位算符不是 `Tm`（而是相对定位的 `Td`/`TD`/`T*`）时**不猜**：该组不平移，
    结果里给出「无法平移相邻片段：…（相对定位）…」并附重叠警告。
  - 平移后若这一视觉行的最右边界越出页面宽度，会给出「⚠️ …超出页面 …pt」警告，**但文件仍然写出**
    （用户可能就是要硬来）。
- **页面坐标是算出来的，不是猜的**：文本渲染矩阵 `Trm = Tm × CTM`，页面上原点 = `(Trm.e, Trm.f)`，
  页面字号 = `Tf 字号 × hypot(Trm.a, Trm.b)`（同时涵盖 `Tm` 缩放与 CTM 缩放）。
  实测那份 WPS 导出的 73 页文档：`Tf 209`、`Tm 0.05 0 0 -0.05 …`、CTM 是一次 y 翻转 →
  `209 × 0.05 = 10.45pt`，与渲染结果一致。逐字 `Td` 相对位移、乱序绘制都不影响定位。
  注意 `Tm` 的操作数在**用户空间**（不是文本空间），所以"页面右移 Δ"换算回锚点用的是
  `[δe, δf] × CTM线性部分 = [Δ, 0]`，而不是 `Δ / |Trm.a|`——实测该文档 CTM 缩放为 1，
  `Tm.e` 就是页面 x，除以 0.05 会多挪 20 倍。
- **重画优先沿用原文的字体家族。** 很多 PDF 的字体是"按名字引用、不内嵌"的
  （`/AUWCNV+TimesNewRomanPSMT`），阅读器用自己的 Times 替换。插件会从目标组字体字典读 `BaseFont`、
  去掉子集前缀，按 `src/core/fonts.ts` 的 PostScript→系统字体表（Times / Arial / Arial Unicode / …）
  解析出文件，**只有当该字体能完整渲染新文字时才用**（fontkit 逐码点检查，汉字会让拉丁字体自动落选）。
  这样 `9.turning` 与右侧的 `around/round 转身` 会是同一家族，字面大小/粗细一致；
  实测 x-height 比值 1.00（此前用 Arial Unicode 时明显偏大，用户截图反馈的就是这个问题）。
- **无法匹配时换字体，但绝不静默**：结果里会出现「原文使用 TimesNewRomanPSMT，但新文字里含它没有的字符，
  已改用 Arial Unicode.ttf，字面可能略有差异」；并会按 x-height / cap-height 比例（拿不到度量时退到
  「原文 run 的 `/W` 宽度推出的等效字号」）把字号估一估以对齐邻居，标注为**估算**。
- **中英混排**即由上面的回退覆盖（拉丁字体画不了汉字 → 换系统 CJK 字体），原字体不动。
- **需要确认**（`destructive`）：先给确认单，带 `confirm=<planId>` 才写盘；缺 `targetId` / `text`
  时按"缺关键参数"处理，**带 confirm 也不能绕过**。`shiftSiblings` 参与 planId——改了它旧令牌即失效。
- 与其它写盘工具一致：默认输出 `<名字>-line-redrawn.pdf`，绝不覆盖源文件。

## 页面与版面
### 页级装配：拆分 / 裁剪 / 重排 / 合并

这四个工具都动"页面"本身（页面框、页序、文件组合），不碰文字与图形的内容流。
它们的输出永远是**新文件**，源文件只读。

#### `pdf_split`：把 2-up 拆成单页（不栅格化）

一张纸印两页的 PDF（A3 试卷、讲义）要拆成单页，最省事的做法是渲染成图片再切——但那样
**文字层、字体、矢量线条全部丢失**，切出来的"试卷"不能搜索、不能复制、打印也发虚。
`pdf_split` 走另一条路：

1. 把页面框（`/MediaBox`、`/CropBox`、`/TrimBox`、`/BleedBox`、`/ArtBox`）改成半页；
2. 在 `/Contents` **最前面**插一条平移 `1 0 0 1 -w/2 0 cm`（右半）或 `1 0 0 1 0 -h/2 cm`（下半），
   把整页内容挪进新框；
3. `/Contents` 是单流还是数组都能处理（数组 `unshift`，单流变成 `[新流, 原流]`）。

内容一个字节都没被重画，所以**文字仍可搜索、可复制**，字体和矢量也原样保留。
平移量按可见区域（`/CropBox ∩ /MediaBox`）计算，页面框原点不在 `(0,0)` 也能切对。

**判定依据是"版式"，与纸张尺寸无关。** 一页能被拆，当且仅当：

- `/Rotate` 为 0（旋转页的"左右"在阅读器里并不是左右，硬切会切错）；
- 长宽比明显偏离 1：`w/h ≥ 1.25`（左右切）或 `h/w ≥ 1.25`（上下切）。

所以 A3 试卷（420×297）能拆，**720×405pt（254×143mm）这种自定义尺寸也能拆**；
正方形或接近 1:1 的单页版式会被判为不规范并跳过（结果里逐页给出中文原因）。

参数要点：

| 参数 | 默认 | 说明 |
|---|---|---|
| `layout` | `auto` | `auto` 按页面方向推断；`left-right` / `top-bottom` 强制切法，方向不符的页会被跳过 |
| `keep` | `both` | `both` 两半都留；`left`/`right` 只留左半/右半；`top`/`bottom` 只留上半/下半。取值与切法不匹配会被拒绝 |
| `gutter` | `middle` | `middle` 严格中线；`auto` 低倍渲染找中缝（见下） |
| `targetSize` | `a4` | **只做信息提示**：切出的每半不是 210×297pt 时会在确认单与结果里写明，但不会因此拒绝执行 |
| `pages` | 全部 | `1-3,7` 这样的页码范围 |

`gutter: middle | auto` 的差别：

- `middle`（默认）严格按中线切。中缝本来就在正中的 2-up（绝大多数试卷）用它最省事，切完每页尺寸一致。
- `auto` 会低倍渲染该页，**以中线为界分左右（上下切则分上下）两半，各取内容包围盒**，
  缝 = 左半内容框的右边界 ↔ 右半内容框的左边界，缝的位置取**间隔中点**。
  - 间隔 < **8pt**、某一半没有内容、或缝偏离中线 > **15%** → **回退中线**，
    并在确认单与结果里写明"未找到可靠中缝…按中线对半"；
  - "有内容"的下限是**一条列/行至少 3% 的暗像素**（`MIN_CONTENT_LINE_RATIO`）：
    中缝里常有浅灰底、扫描噪点、被打断的细虚线，不设下限的话内容框会一直顶到中线，
    把本来分得很开的两栏误判成"没有缝"。
  - 注意：`auto` 测的是**内容框之间的间隔**，不是两条边框之间的视觉缝；内容相对边框内缩很多时，
    中点会比视觉缝偏一些。缝本就在中线的文档用默认的 `middle` 更稳。

**一个真实场景：答案版 + 空白版并排的讲义。**
像 `化学一轮复习重点小考（4）.pdf`（10 页，每页 720×405pt，左栏红字答案、右栏同题留空）这种文件：

- 要**学生版**（只有空白题）：`pdf_split path=… keep=right` → 10 页，每页 360×405pt；
- 要**答案版**：`keep=left` → 同样 10 页；
- 要**两份都留**：`keep=both`（默认）→ 20 页，顺序是 `A1,B1,A2,B2,…`，
  想再分成"答案册 / 空白册"可以用 `pdf_arrange order=odd-even`：
  奇数页（也就是每张的左半、答案版）全部排到前面，偶数页排到后面。

`keep` 是按用户诉求加的参数：这类讲义用 `keep=right` 一步就得到只含空白题的册子，
不必先拆 20 页再删一半。`keep` 参与 `planId`，改了它旧确认令牌立即失效。

#### `pdf_crop`：批量裁剪（只裁不缩）

只改页面框，**绝不缩放**页面内容：改框只是决定"看哪一块"，比例和字号都不变。

- `mode: fixed`（默认）：所有页用同一个矩形 `box: {left,bottom,right,top}`（pt，原点左下）。
  越界会被收拢到页面可见区域，并在结果里逐页提示；
- `mode: trim`：逐页低倍渲染找内容边界（暗像素包围盒）再加 `margin`（默认 6pt）留白。
  `uniform: true`（默认）时取所有页边界的**并集**，保证裁完每页尺寸一致；
- 默认同时把 `/MediaBox` 与 `/CropBox` 设为裁切后区域；`setCropBoxOnly: true` 只改 `/CropBox`；
- 缺 `box`（`mode=fixed`）走"缺关键参数"：先给确认单，带 `confirm` 也不能绕过。

结果里逐页给出裁切框与"裁掉了多少面积（比例）"。

#### `pdf_arrange`：重排页序（只改顺序与 `/Rotate`）

- `order`（必填）：显式列表 `1,3,5`、区间 `1-3,7,4-6`、或预设
  `odd-even`（先所有奇数页、再所有偶数页）/ `reverse`（逆序）/ `swap-pairs`（`2,1,4,3,…`）；
- `delete`：按**原文件页号**删除，与 `order` 不能重叠（重叠会被拒绝）；
- `rotate: {pages: "1-3", angle: 90}`：`pages` 指**重排后**的页号，只改 `/Rotate`
  （归一化到 0/90/180/270），不动内容——这是"把横放的页面转正"的正确做法；
- 它**不裁剪、不缩放**，页面几何原样带过去。

非法顺序、越界页号都给中文错误（例如 `顺序里的第 9 页超出文档页数 6`）。

#### `pdf_merge`：按顺序合并

`paths` 至少 2 个文件，`ranges` 可选、与 `paths` 一一对应（`["1-3","","5"]`，空串表示整份）。
结果逐文件报出取了哪些页、每页来源。输出默认落在第一个文件所在目录
（`<第一个文件名>-merged.pdf`），绝不覆盖任何源文件。

#### 确认门控

四个工具**一律归 `destructive`**（`src/core/confirmation.ts` 的 `PAGE_ASSEMBLY_TOOLS`）：
它们产出的是"另一份文件"，但改的是页面结构、页序与几何，出错时用户拿到的是一份
"看起来对、其实错了"的文件——那比直接报错更难发现。所以未确认**绝不落盘**，
`plan` / `confirm` / `force` 三个参数与其它写盘工具一致。

另外：拆分时如果**选中的页全部**不规范（旋转 / 比例接近 1 / `keep` 与切法不匹配），
工具会走 `authorize` 的 `refused` 分支，逐页给出中文原因并直接拒绝，不会产出一份空文件。

### 版面重排（`pdf_layout`）

| action | 做什么 | 关键参数 |
|---|---|---|
| `resize` | 把每页内容**等比缩放**到统一纸张并居中（**不栅格化，文字仍可搜索**） | `pageSize`（`a4`/`a4-landscape`/`a3`/`a5`/`letter`/`legal`）、`mode=fit\|stretch`、`margin`、`pages` |
| `nup` | 每张纸放 N 页（拼版省纸） | `perSheet=2\|4\|6\|8\|9`、`pageSize`、`margin`、`gap` |
| `booklet` | 按骑马钉顺序生成"对折装订"的版面 | `pageSize`（默认 `a4-landscape`） |

要点（真机实测）：

- `resize` 走"复制页面 + 改 `/MediaBox` + 内容流前插缩放矩阵"，**不嵌套 XObject**——比 `embedPage` 方案小 37KB，且文字保持原生可搜索。
- **缩放不会带注释一起缩**：注释的 `/Rect`、`/QuadPoints` 与表单域坐标在页面坐标系里，不随内容缩放。
  有注释时结果与确认单里会明确提示「N 个注释/表单域的位置没有跟着缩放，请核对」。
- **`nup` / `booklet` 会丢掉源页注释**（用嵌入页面的方式实现），同样会明确提示。
- `booklet` 的对折顺序：第 1 面 = 「最后一页 + 第 1 页」，第 2 面 = 「第 2 页 + 倒数第二页」……打印后对折即可成册。
- 需要的不是"改尺寸"而是"裁掉边缘"时，请用 `pdf_crop`（只裁不缩）。

### 图片与 PDF 互转（`pdf_images`）

| action | 做什么 | 关键参数 |
|---|---|---|
| `export` | 页面 → 图片，每页一个文件 | `pages`（默认全部，支持 `1-3,7`/`odd`/`even`）、`format=png\|jpeg`、`scale`（**1=72dpi、2=144dpi、3=216dpi**）、`quality`（JPEG，默认 0.9）、`outputDir`（默认源文件旁 `<名字>-pages/`） |
| `build` | 多张图片 → 一个 PDF，按 `images` 数组顺序 | `images`（png/jpg **可混用**）、`pageSize=a4\|letter\|fit`（默认 fit：页面等于图片尺寸）、`margin`（pt）、`output` |

要点：

- **导出是栅格化**：文字变成图片，**不可搜索**——要可搜索请对原 PDF 用 `pdf_make_searchable`，或直接用 `pdf_extract_text`。
- 倍率与 DPI 的换算：PDF 用户单位是 1/72 英寸，所以 `scale=2` ≈ 144dpi，打印级清晰度一般用 `3`。
- `build` 用 `pageSize=fit` 时不做任何缩放（页面正好等于图片）；用 `a4`/`letter` 时按"等比缩放 + 居中 + 边距"排布。
- 两个 action 都是写盘操作：**走确认门控**，未确认不生成任何文件；源 PDF/源图片都不会被改动。

## 表单与文档属性
### 表单（`pdf_form`）

| action | 做什么 |
|---|---|
| `list` | 列出字段：名字｜类型（文本/勾选框/单选/下拉/列表）｜当前值｜可选项（**只读，不弹确认单**） |
| `fill` | `values={字段名: 值}` 填值；`flatten=true` 可填完顺手压平 |
| `flatten` | 把表单压平成静态内容（**不可再编辑**，适合归档/发布） |

要点：

- **中文能填**：pdf-lib 默认用 Helvetica 画字段外观，中文值会抛 `WinAnsi cannot encode`；
  本工具在填完后用系统的 CJK 字体重刷字段外观，所以中文表单才真正可用。
- **字段名写错会报错并列出该文件真正可用的字段名**，不会静默跳过（否则你以为填上了）。
- `fill` 不压平时字段仍可编辑；`flatten` 之后文字变成页面普通内容（不可搜索性不受影响，但不能再当表单填）。
- `fill` / `flatten` 走确认门控（写盘）；`list` 是只读直通。

### 文档信息与书签（`pdf_metadata`）

| action | 做什么 |
|---|---|
| `get` | 读 6 个属性（title/author/subject/keywords/creator/producer）+ 页数 + 书签条数（**只读**） |
| `set` | `values={title, author, …}` 写属性，**支持中文**（UTF-16 编码，`PDFHexString.fromText`） |
| `clear` | 清空 6 个属性 + 删除创建/修改时间（**对外发布前去隐私**） |
| `outline-list` | 列出书签（含目标页，嵌套按深度缩进，**只读**） |
| `outline-set` | `outline=[{title, page}]` 生成书签（**当前只支持一层**） |
| `outline-clear` | 删除书签（去掉 `/Outlines`） |

要点：`/Dest` 写的是 `[页面引用 /Fit]`——写页码数字多数阅读器不跳转；中文标题必须用 hex 字符串，
用 `PDFString.of('中文')` 会存成乱码。书签嵌套尚未实现（文档里写明，不假装支持）。

## 安全与隐私
### 矩形密文（`pdf_redact`）

只画黑框是**假密文**：文字还在内容流里，复制/搜索/提取照样拿得到。所以这里**真删**：
定位文字绘制指令 → 与矩形求交 → 从内容流里把操作数换成空串 → 再补色块。

| action | 做什么 |
|---|---|
| `preview` | 空跑：报告会删掉多少条文字指令、多少个注释，**不写任何文件** |
| `apply` | 真删并写盘（走确认门控） |

要点与**已知边界**（重要）：

- **写盘前强制复核**：框内原本能提取到的文字，若在结果里仍能提取到，就**拒绝输出**并说明原因。
  宁可明确失败，也不给"看起来涂黑了、其实还能复制"的假密文。
- **当前档位：单段内容流的页面**（有回归测试保证）。真实复杂文件（一页多段流、正文嵌在多层
  Form XObject、文字带 CTM 变换）**命中率不足，会被护栏拦住并拒绝输出**；ROADMAP 里标为受限。
- **扫描件（整页图片）不做内容修补**——图片像素在 XObject 里，真删需要重画像素或栅格化整页，
  与"不引入重依赖、不做图片内容修补"的纪律一致。工具会识别这类页并**如实说明**，只做视觉遮盖。
- 需要绝对可靠时：`pdf_images action=export` 导出这几页 → 图片上涂黑 → `pdf_images action=build` 重新合成。
- 落在框里的注释会一并删除（注释正文也可能泄露信息）。

## 维护与比对
### 体积与结构优化（`pdf_optimize`）

`profile=gc`（默认，垃圾回收）/ `linearize`（线性化）/ `both`（走 qpdf 重写对象层）/ `compare`（两版差异，见下）。

**诚实预期（实测）**：图片占主导的文档可能只省 ~2%，也可能**不变甚至略增**（对象流本身有开销）。
工具会明确报出「优化前 → 优化后」字节数与 `qpdf --check` 结果；**若体积没降就别用这次的结果，直接用源文件**。
想真正大幅变小，走 `pdf_images action=export` 导出 JPEG（会栅格化，文字不可搜索）。

### 两版差异（`pdf_optimize profile=compare`）

```
pdf_optimize path="定稿v1.pdf" profile="compare" other="定稿v2.pdf"
```

**逐页比对文字层**，报告"哪些页变了、具体增删了哪些行"（`+ 新增行` / `- 删除行` / 新增页 / 删除页）。
**只读**：不写盘，即使策略是 `destructive` 也直接给结果。

- 以文字层为准（可复现、可断言），**纯排版/颜色/图片变化不会体现在结果里**。
- 扫描件（整页图片）没有文字层时会**如实报告"无法按文字比对"**，并建议先 `pdf_make_searchable`
  或用 `pdf_images` 导出图片人工比——不会假装"没有差异"。

## 批量
### 目录批量处理（没有 `pdf_batch` 工具，这是刻意的）

批量本质是**编排**，不是 PDF 内部操作——用一个循环调用现有工具即可，所以不再单独增加工具
（守住工具总数）。典型配方：

```
# 对一个目录里的每份 PDF：先统一尺寸、再编页码、最后优化
pdf_layout    path="in/报告1.pdf" action="resize" pageSize="a4" output="out/报告1-a4.pdf"
pdf_text      path="out/报告1-a4.pdf" action="page-number" output="out/报告1-页码.pdf"
pdf_optimize  path="out/报告1-页码.pdf" profile="gc" output="out/报告1-定稿.pdf"
# …对 in/ 里其余文件重复；每步都会先给确认单，写盘前可核对
```

需要注意：每个工具都会独立走确认门控（未确认不落盘），批量时请逐个确认，
或对明确安全的一步使用 `confirm` 令牌。

## 检索辅助
### 定位答案页（`pdf_find_answers`）

"这份 PDF 哪几页是答案？"以前只能靠助手逐页看图或 OCR 猜——同一份文件问两次可能得到两个答案。
`pdf_find_answers` 把它变成**可复现的打分**：给出候选页范围、中文依据与置信度，**只读、不删改、不擅自拆分**。

它**不接确认单参数**（没有 `plan` / `confirm` / `force`）：正常调用不会出确认单。唯一的成本门控是
"整档 OCR 超过 **20** 页"，判定口径与 `pdf_extract_text` 完全一致（同一个 `OCR_WHOLE_DOC_PAGES`）——
数据里有人把 pages 省略（或给的页范围覆盖全部页）且 `ocr` 为真时才算"整档"。策略是 `always` 时会返回确认单，
提示把 `pages` 拆成不超过阈值的几段分别调用（本工具没有令牌参数，所以不是"带 confirm 继续"那条路）。

判定依据与权重（`src/core/answer-pages.ts` 的 `ANSWER_PAGE_WEIGHTS`，改这里必须同步本节）：

| 依据 | 权重 | 说明 |
|---|---|---|
| 答案标题词 | **+5** | 页首 200 字内出现「答案」「参考答案」「答案与解析」「答案速查」「评分标准」「试题解析」「答案及解析」；英文认 `Answer Key` / `Answers` / `Solutions` / `Mark Scheme`（比较前去掉空白，容忍 OCR 塞进去的空格） |
| 答案速查表 | **+4** | **连续递增**的 ≥5 组「题号 + 单个字母」（`1 C`、`2. A`、`3、D`…），或等长的连续块 `1-5 CBDAB` |
| 解答句特征 | **+2** | 「解：」「证明：」「答：」「∴」「∵」「由…得…」合计出现 ≥2 处 |
| 题干特征 | **−2** | **每类各算一次**：「（本小题 N 分）」「（本题 N 分）」「每小题 N 分」「解答应写出文字说明」「如图」「已知」「求证」 |
| 位置先验 | **+0.5** | 只在总分绝对值 ≤ 1 **且**本页位于文档末 25% 时加，依据里必须写「仅依据位置推断，置信度低」。**这种页不算候选**：单独列在「位置推断（仅供参考，不建议据此拆分）」一节，不进 `answerRanges`、不进 `order` |

结论：总分 ≥ 2 → `答案`（≥5 分记 `高`）；≤ −2 → `试卷`；|总分| ≤ 1 → `无法判定`（除非位置先验生效）。
**候选区间与拆分建议只使用 medium/high 的页**；`low`（含纯位置先验）只出现在「位置推断（仅供参考）」一节，
若整份文档只有这种页，结论是 `未找到答案页（仅第 N 页位置可疑，无文本证据）` 且不给拆分建议。
答案侧特征（标题词/速查表）与 **≥2 类**题干特征同时出现 → `mixed`，依据里两侧都写出来。

#### 为什么速查表要"连续递增"

真实试卷的选项列表就是 `A,5 B,4 C 3 D,2`——每个选项值后面紧跟着下一个选项字母，凭空造出
3 组「数字+字母」，一份 9 题的试卷能凑出 **15** 组。所以只数"数字+字母"会把纯题目页误判成答案页
（修复前 `2025.10沈阳43中八上数学月考试卷+答案.pdf` 的第 1 页就是这么误报的）。
真正的答案速查表有两个结构特征：题号**严格递增 +1**，且相邻两对**挨得很近**（间隔 ≤ 24 字符）；
选项列表的数字是递减的、或同一数字重复，因此被排除。字母认 **A–F**（有些卷子选项到 F）；
"连续递增 +1"与"间距 ≤ 24 字符"这两条是挡住误报的关键，不能放宽。

#### 完整流程：候选 → 确认 → `pdf_arrange`

```text
1) pdf_find_answers path="试卷+答案.pdf"
     → 答案页候选：第 7 页（置信度 高）
       逐页判定：第 1 页｜试卷｜-2｜…  第 7 页｜答案｜9｜页首出现答案标题词：答案（+5）；答案速查表…（+4）
       拆分建议：
         pdf_arrange path="…/试卷+答案.pdf" order="1-6" output="…/试卷+答案-试卷.pdf"
         pdf_arrange path="…/试卷+答案.pdf" order="7"   output="…/试卷+答案-答案.pdf"
2) 看依据确认候选对不对（不对就别执行，或改口说清哪几页是答案）
3) 复制上面两条 pdf_arrange 命令（或让助手直接调）→ 得到"试卷"与"答案"两个新文件
```

`pdf_arrange` 只按 `order` 重新排列页面（这里等价于挑出子集），**不改几何、不缩放**，
两条命令产出的都是新文件，源文件不动。工具给的建议只是"可复制的下一步"，**它自己不会去拆**。

参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `pages` | 全部 | 要判定的页范围，例如 `5-7`；只判定给定页（范围外连文字层都不读），此时不给整档拆分建议 |
| `ocr` | `true` | `false` 时只读文字层：图片页标 `无法判定` 并写明"未做 OCR"，**绝不猜**（与 `pdf_extract_text` 的 `ocr` 不同——那个目前只影响成本判定，见「已知限制」） |
| `lang` | `chi_sim+eng` | OCR 语言。语言数据目录里缺失的语言会被**显式退化**（结论里写明原因，例如"eng 只有裸文件 .traineddata、当前需要 .gz，已退化为 chi_sim"），全部缺失则中文报错——不会让 tesseract 崩进程 |
| `langPath`（仅插件配置） | 见下 | 语言数据目录 `<lang>.traineddata[.gz]`。**不是参数**，由插件配置 `tessdataPath` 或环境变量 `DSH_PDF_STUDIO_TESSDATA` 指定；都不给才落到兜底的跨项目路径（那台机器上没有就会退化为"语言数据缺失"中文报错） |

#### 边界（这些情况下它会说"不行"，而不是硬凑）

- **答案与题目同页**（`mixed`）：不给拆分建议，只提示"第 N 页答案与题目同页，无法按页分离"。
  本工具**不做内容级分离**（不会去擦掉题目、也不会按区域裁半页）——那需要逐页版式分析，
  目前只会如实报告。
- **答案与题目交替**（`1:题 2:答 3:题 4:答`）：给多段候选区间，但**不给"两段式"拆分建议**（那样会切错）。
- **手写答案 / 多列答案表 / 半页答案**：OCR 对手写体识别率低，多列排版的"连续递增"可能被列间距打断，
  半页答案页则可能同时命中题干特征变成 `mixed`。这三种情况都可能判成 `无法判定` 或 `mixed`——
  工具不会为了给你一个答案而降低标准；此时请人工确认页码后再用 `pdf_arrange`。
- **纯图片且 `ocr=false`**：一律 `无法判定`，并说明"未做 OCR"。

## 交互模型与调用约定

**浮层面板不再是主界面**（它作为可选浮层保留：profile 里设 `surface: true` 才注入）。
之前那版是"先把面板摆在你眼前、再让你填表"——那是把一个桌面应用
硬塞进对话界面，插件在你还没有任何结果时就索取注意力。现在默认是最初需求描述的那种交互：

> 用自然语言说要做什么 → Agent 调用工具 → 结果回到会话里

页面上什么都不出现；确认单也以纯文本返回（见「执行前确认」）。

注册了 **21 个工具**：

| 工具 | 作用 |
|---|---|
| `pdf_inspect` | 页数 / 尺寸 / 是否加密 / 按页类型；可选列出可编辑文字块（含 id） |
| `pdf_extract_text` | 提取文字与行坐标（文字层或 OCR） |
| `pdf_find_answers` | **定位答案页候选**：候选页范围 + 中文依据 + 置信度（只读，不拆分；答案与题目同页时如实报"无法按页分离"） |
| `pdf_annotate` | **注释标注**：高亮 / 下划线 / 删除线 / 方框 / 椭圆 / 自由文本 / 便签 / 图章，写进注释层（可选中、可编辑、可导出，带 Print 标志） |

### 一个会让工具完全无法运行的坑

宿主用 `assertRenderedContent` 校验 `output.render` 的返回值：

```js
✓ return [{ type: 'text', text: String(value) }]   // 必须是内容块数组
```

我一开始返回的是 `{ content: [...] }` —— **类型上说得通、我自己的测试也全绿，但真正被调用时会立刻抛错**。
因为我的测试断言的正是我自己编错的约定。现在改成数组，并加了一条针对该约定的断言。

### 一个实现上的坑

工具对象是**本模块自己构造**的，不是用 `defineTool` 生成的。

原因：`@deepseek-ai/dsh-tools` 能从 **profile** 解析，但**不能从本插件的真实路径解析** ——
插件是用 `link:` 安装的，Node 会把软链解析到真实路径，于是 bundle 里那句
`import('@deepseek-ai/dsh-tools')` 会抛 `MODULE_NOT_FOUND`，尽管 profile 明明能解析它。
依赖它就意味着要自带一份宿主包的副本并祈祷版本一致。

所以我读出了 `defineTool` **实际产出的对象结构**（`{name, description, parameters, output:{schema,render}, execute, presentCall}`），
自己构造，并自带一个小 schema 编译器（约 40 行）把参数规范编译成 JSON Schema。
顺带自己做了参数校验，好让模型的非法调用得到可读报错。

过程中发现 schema 子集的两条硬规则：**`additionalProperties` 必须是显式布尔值**（嵌套对象上），
而**值 schema 不接受 `required`**。这两个都是撞了报错才知道的。

### 顺带修掉一个真 bug

`inspectDocument` 少了 `ignoreEncryption`，导致**检查加密文件时直接抛异常**——
而"这个文件加密了吗"恰恰是调用方最需要答案的场景。现在能正确报告已加密。

### 计划与确认参数（`plan` / `confirm` / `force`）

除只读的 `pdf_preview` 外，**其余 11 个**工具都额外带这三个统一参数：

| 参数 | 类型 | 语义 |
|---|---|---|
| `plan` | boolean | 只返回执行计划（确认单），不做任何写入。即使该操作本来不需要确认，也会返回计划。 |
| `confirm` | string | 确认令牌：把上一次返回的**完整** `planId` 原样传回即执行；参数、输入文件或输出路径变了会被拒绝。 |
| `force` | boolean | 跳过确认直接执行。**危险逃生舱，仅供脚本与测试显式使用**，不要让助手替你加。 |

`pdf_watermark action=scan` 与 `pdf_protect action=check` 是只读分支，在到达闸门之前就返回了，
传 `plan: true` 也不会给出计划。判定细节见「执行前确认」。

### 会话内预览（不需要客户端插件）

竞品那种"实时预览窗口"我原以为要写客户端插件。查了它的源码后发现**不用**：

```js
// dsh-univer-office 的 screenshotTool
render: (_args, value) => [
  { type: "text", text: JSON.stringify(value) },
  ...value.result.images.map(item => ({ type: "image", attachment: imageRef(item.image) })),
]
```

**图片作为 `{type:"image", attachment:ref}` 内容块返回，由内置的图片卡片渲染。**
所以 `pdf_preview` 工具就能把页面渲染成图片直接显示在会话里，零客户端风险。

### 设计规则

- **破坏性操作永不覆盖源文件。** 每个产出文件的工具都接受可选 `output`，默认写到源文件旁的
  新文件；显式指定源文件本身会被拒绝（有测试覆盖）。这条保证是 Agent 可以无人值守调用它们的前提。
- **昂贵操作必须显式开启。** `pdf_inspect` 默认只读几何信息（约 10ms）；完整分诊要 `analyze=true`，
  因为扫描件的 OCR 是每页数秒级——静默花掉三十秒比先问一句更糟。
- **模棱两可要报告，不要猜。** 判断不了的水印带着置信度和理由返回，并保持原样不动。
- **写盘前先过确认闸门。** 破坏性操作、有歧义的操作（以及配成 `always` 时的高成本操作）先返回确认单，
  人确认后才执行。见「执行前确认」。

## 执行前确认（写盘前的人闸门）
### 为什么需要它

工具一旦被调用就必须返回结果，**没有中途反问的机会**。而普通用户的诉求常常是模糊的
（"帮我把这个 PDF 弄一下"），于是最常见的失败方式不是报错，而是**"看起来成功"**：
改到了错的文件、改错了页、什么都没改却说"已生成"。

所以「确认」做的不是一句"确定吗"，而是一次**可校验的握手**：

1. 工具在写盘前先算出这份操作计划（文件指纹、参数与默认值、影响面、可纠正项），返回给上层；
2. 人看到计划后确认——**默认这条路径是纯文本**：确认单直接回到会话里，用户对助手说「确认执行」；
   开了 `surface: true` 时，同一份计划还会出现在浮层的「待确认操作」卡片里（可选路径，机制完全相同）；
3. 上层带着 `confirm: <planId>` 再调一次，宿主**重新计算** planId 并比对——一致才写盘。

确认流程与是否注入浮层**无关**：不注入时一样能用，`/api/pdf-studio/plans` 那三个接口也照常注册。

实现分别在 `src/core/confirmation.ts`（类别判定、planId、计划库、`authorize`）与
`src/host/tools.ts`（每个工具的 `authorize({...})` 调用点）。

> 面向普通用户的提示词模板（7 个可直接复制的写法、意图对照表、反例）见 [docs/PROMPTING.md](docs/PROMPTING.md)。

### 三类门控

| 门控 | 含义 | 当前触发点（逐个核对过 `authorize` 调用） |
|---|---|---|
| `destructive` | 会改内容或覆盖已有文件 | `pdf_edit_text`（改写正文文字）；`pdf_replace_line`（整行重绘：抹掉绘制组原文并重画）；`pdf_watermark action=remove`；`pdf_protect action=encrypt` / `decrypt`；**任何工具的输出文件已存在**（会被覆盖） |
| `expensive` | 代价高 | `pdf_inspect analyze=true`（深层分诊，扫描页逐页 OCR）；`pdf_extract_text` 整档提取且页数 **> 20**；`pdf_find_answers` 整档判定且 `ocr` 为真、页数 **> 20**（与 `pdf_extract_text` 共用同一个门槛，因为都是逐页 OCR）；`pdf_make_searchable` 页数 **> 20** |
| `ambiguous` | 会导致"猜"的地方 | 缺少关键参数（如 `pdf_watermark action=add` 没给 `text` / `imagePath`）；路径候选 **> 1** 个文件；整档操作且页数 **> 200**；工具自己发现的歧义 |

判定优先级 `destructive` > `ambiguous` > `expensive`：`gate` 只取其中一个，全部理由留在 `gateReasons` 里。
阈值都定义在 `src/core/confirmation.ts`：`OCR_WHOLE_DOC_PAGES = 20`、`SEARCHABLE_PAGES = 20`
（整档 OCR 与可搜索化共用同一门槛）、`HUGE_DOCUMENT_PAGES = 200`；计划有效期 `PLAN_TTL_MS = 15 分钟`。

### 三种策略

`requiresConfirmation(gate, policy)` 的三档语义（与 `src/core/confirmation.ts` 里的函数注释一字对应）：

| 策略 | 行为 |
|---|---|
| `never` | 从不问 |
| `destructive`（**默认**） | **会改文件**或**有歧义**就问——歧义意味着"可能做错事"，在改文件之前问一句比事后解释便宜得多 |
| `always` | 上面两类 **+ 高成本**（整档 OCR、深层分诊 `analyze=true`、超过 20 页的可搜索化）都问 |

配置优先级：插件配置 `requireConfirmation` > 环境变量 `DSH_PDF_STUDIO_CONFIRM` > 默认 `destructive`。
注意 `gate = 'none'` 的操作**任何策略都不会问**（包括 `always`）——例如给一个新输出路径加水印、
或把 `mode=invisible` 的可搜索 PDF 写到还不存在的文件上。

**OCR 语言数据目录**（只影响走 OCR 的工具）用的也是同一套优先级：
插件配置 `tessdataPath` > 环境变量 `DSH_PDF_STUDIO_TESSDATA` > `src/core/ocr.ts` 里的兜底绝对路径。
那个兜底路径指向的是另一个项目（`dsh-pdf-maker`）的资源目录，**别人机器上必然不存在**，所以换机器请显式配一个：
目录里要放 `<语言>.traineddata` 或 `<语言>.traineddata.gz`（两种形式**混装也能跑**：
工具会按选定的 gzip 模式逐语言核对，不匹配的语言退化掉并在结果里写明，不会把 tesseract 崩掉）。

完整的策略矩阵：`never` 全不问；`destructive` 只对 `destructive` 与 `ambiguous` 返回真；
`always` 对 `destructive` / `expensive` / `ambiguous` 都返回真；`none` 在三档策略下都是假。

### planId 校验拦住了什么

planId 由「工具 + 动作 + canonical 化参数 + 输入文件指纹（路径 / 大小 / mtime）+ 输出路径及是否覆盖」哈希而成
（`computePlanId`，带算法版本号；**不含时间戳与状态**，所以执行时能重算出同一个值）。于是：

| 情况 | 结果 |
|---|---|
| 改了参数（换页、换颜色、换水印文字…） | 重算的 id 不同 → **拒绝执行**，并逐条列出差异 |
| 换了输入文件（或计划生成后文件被改过） | 文件指纹变了 → **拒绝执行**：`输入文件已变化：计划基于 … 现在是 …` |
| 输出路径不同 | **拒绝执行** |
| 计划过期（> 15 分钟） | **拒绝执行**（有效期在**执行时**判定，在浮层里点「确认执行」也不会让过期计划复活） |
| 计划已被取消 | **拒绝执行**：`已被取消，未执行任何操作` |
| 计划执行过一次 | **拒绝执行**：计划是一次性的（`consumed`） |
| 计划 id 不认识 | **拒绝执行**：`不存在或已过期（计划保留 15 分钟）` |

> `confirm` 也可以给**唯一前缀**：长度 ≥ 6 且只匹配到一份计划时接受（浮层卡片只显示前 8 位，
> 用户照抄那 8 位正好够）；匹配到多份会拒绝并要求用完整 id，匹配不到按"不存在或已过期"处理。

### 缺关键参数不能靠确认绕过

`ambiguous` 里"必须靠猜"的情况不当作"问一句就能继续"，**也不看 `requireConfirmation` 策略**：

- **缺关键参数**（例如 `pdf_watermark action=add` 没给水印文字或图片）：先返回一张写明缺什么的确认单；
  此时**带着 `confirm` 再调也会被拒绝**——因为执行时只能退到插件默认值（例如水印文字 `WATERMARK`），
  那是在替用户瞎猜。必须补齐参数、重新生成计划。
- **名称对应多个文件**：直接把候选列出来要求指明路径，不生成可执行计划。

### 计划的生命周期与接口

状态机：`pending → confirmed | cancelled | expired | consumed`。计划库在**内存里**（`Map`），
终态计划在 `2 × TTL` 之后回收，避免内存无限增长。

这三个接口**与是否注入浮层无关**——它们操作的是同一份计划：

| 接口 | 说明 |
|---|---|
| `GET /api/pdf-studio/plans` | 待确认计划列表（只列 `pending`）；开了 `surface: true` 时浮层每 **3 秒**轮询一次 |
| `POST /api/pdf-studio/plans/{planId}/confirm` | 标记为已确认（浮层「确认执行」按钮走的就是这个接口） |
| `POST /api/pdf-studio/plans/{planId}/cancel` | 标记为已取消（浮层「取消」按钮同理） |

### 可选路径：浮层卡片

开了 `surface: true` 时，页面上的「待确认操作」卡片包含：中文标题、门控标签（破坏性 / 高成本 / 有歧义）、
planId 前 8 位、剩余时间、多行确认单、可纠正项与歧义列表，以及「确认执行」「取消」两个按钮。
卡片内容全部用 `textContent` 写入，标题与确认单里的 HTML 只当文本显示（有专门的转义测试）。
接口不可用时只显示一行灰字「计划接口暂不可用」，不弹窗、也不丢已经看到的计划。
轮询随面板开关启停，另有 `window.__dshPdfStudioStop()` 可显式停掉（测试与卸载用）。

注意卡片上的按钮只改计划状态：点「确认执行」后，还要对助手说一句「继续执行计划 …」，
助手才会带着 `planId` 再调一次工具。**不开浮层时这一步同样成立**，只是"确认"这句话直接对助手说即可。

那份多行确认单（`renderSheet`，浮层与文本共用同一份）按固定顺序输出：
`文件：`（每个输入文件一行，带 basename / 大小 / 最后修改时间）→ `动作：`（中文标题）→ `参数：` →
`默认值：…（你没指定，用了这些）`（有默认项时）→ `原因：…`（仅当 `gate !== 'none'`，门控原因，多条用「；」连接，
让用户先看见"为什么被拦下来"）→ 每条 `影响：` → `待确认：`（歧义项）→ `要改哪一项直接说，例如：`。

工具返回给模型的纯文本计划（`renderPlanPrompt`）是同一份 `sheet`，措辞不会两处漂移：
先一行 `⚠️ 这个操作需要你确认后才会执行。`，然后是确认单、`计划 id：p_…（15 分钟内有效）`，
以及"确认后请对助手说「确认执行」"。

### 已知限制

- **确认的主路径是文本**：确认单直接回到会话里，用户对助手说「确认执行」，助手带 `confirm=<planId>` 重调。
  浮层按钮（`surface: true` 时才有）是**可选的第二条路径**，且它本身是用户主动点击，不走确认单流程。
  卡片上显示的 id 只有前 8 位（方便口头指认）；`confirm` 接受 ≥6 位的唯一前缀，也可以给完整 planId。
- **计划库存在内存里，进程重启即清空**；计划默认保留 **15 分钟**，且是**一次性**的（执行过即 `consumed`）。
- `force: true` 跳过全部判定，**只应出现在脚本与测试里**。它连"缺关键参数"也能放行——
  那正是它必须被显式使用的原因。
- `pdf_extract_text` 的 `ocr` 目前**只影响成本判定，不影响实际提取**：缺省视为开（整档提取按 OCR 计入
  「> 20 页」门控），显式传 `ocr: false` 则不按整档 OCR 计入该门控——但引擎对图片页**仍然会走 OCR**。
  工具提示里的"只要文字不要 OCR 就加 `ocr=false`"对当前实现不成立。
- 水印能力边界不变：栅格化进页面图片的、或当正文绘制的水印**无法可靠移除**（`scan` 会说明原因）。
  确认闸门只保证"不做没被同意的事"，不改变某个操作本身能不能做成。
- `pdf_watermark action=remove` 的 **`minConfidence` 是确认单的一部分**：计划会写明"只移除置信度 ≥ X 的候选"，
  改这个值就要重新确认。默认 0.9 —— 页眉/页脚类 artifact 候选（0.7）**不会被默认删掉**。
- **`pdf_edit_text` 不做重排，但改长/改短一个词用 `pdf_replace_line` 解决**：`pdf_edit_text` 只把
  指定文字块的字形串换掉、**不会移动后面的文字**，所以它只适合**等长/原地替换**（`Unit` → `unit`）；
  把一个词改长（`turn` → `turning`）时它会给出「超过原 N pt，可能向右溢出」的提示但**不会阻止**，
  渲染出来就是与后一个字重叠。**要改长/改短请用 `pdf_replace_line`**：它抹掉该文字块所在的整个
  `BT … ET` 绘制组，再在算出的页面坐标原点重画长度自由的新文字，并把**同一视觉行右侧的兄弟组
  整体右移**让位（默认 `shiftSiblings: true`，见上文「整行重绘」）。
  代价是它作用在"整组"而不是"那一句"上——组里还有别的文字时，要么整组一起重写，要么继续用
  `pdf_edit_text` 做等长替换。若右侧组用相对定位（`Td`/`TD`）锚定、或平移后会越出页面，
  插件**不会静默处理**：前者不平移并给重叠警告，后者写出文件但给出「超出页面」警告。
- **`pdf_find_answers` 只给候选，不做内容级分离**：答案与题目同页（`mixed`）时不拆分；
  手写答案、多列答案表、半页答案可能判成 `无法判定`/`mixed`。位置先验只在 `|总分| ≤ 1` 且末 25% 页时
  加 0.5 并且会写明"仅依据位置推断，置信度低"——它**不是证据**：这种页单独列在「位置推断（仅供参考，
  不建议据此拆分）」一节，**不进候选区间、不进 `pdf_arrange order`**；若整份文档只有这种页，结论是
  `未找到答案页（仅第 N 页位置可疑，无文本证据）`，也不给拆分建议。详见「定位答案页」一节。
- **OCR 语言数据缺失/混装时会显式退化**：`pdf_find_answers` 的 `lang` 默认 `chi_sim+eng`。工具在创建
  worker 之前按**选定的 gzip 模式逐语言**核对存在性（不是"看第一个语言就定全局模式"，也不是"有 .gz 或裸文件就算可用"），
  不匹配的语言退化掉并在结论里写明原因，例如
  「请求 lang=chi_sim+eng…eng 只有裸文件 .traineddata、当前需要 .gz，已退化为 chi_sim」；
  请求的语言**一个都没有**时才给中文错误。这条检查是必需的：tesseract 在语言文件缺失时抛的是
  worker 的**未捕获异常**（`ENOENT …/eng.traineddata.gz`），`try/catch` 接不住，会直接打崩宿主进程——
  混装目录（`chi_sim` 有 `.gz`、`eng` 只有裸文件）正是这么崩的。
  语言数据目录本身可配置：插件配置 `tessdataPath` > `DSH_PDF_STUDIO_TESSDATA` > 兜底的跨项目绝对路径。
- **页级装配（拆分 / 裁剪 / 重排 / 合并）的边界**：
  - **拆分不缩放，只改纸张边界。** 切出来的页面尺寸就是原页的一半（A3 → 210×297 是 A4，
    但 720×405 会切成 360×405）。**要 A4 可打印尺寸必须先缩放/拼版——当前版本不做，也没有 `fit` 参数**，
    工具只会在确认单与结果里提示"不是 A4"。
  - 拆分只支持**规范 2-up 版式**（`/Rotate` 为 0 且长宽比 ≥ 1.25）；旋转页、正方形/单页版式会被跳过，
    结果里逐页给出中文原因。它也不按半边拆分**批注/表单域**：页面上的批注会随页树一起保留。
  - `gutter: auto` 测的是"左右内容框之间的间隔"的中点，不是两条边框之间的视觉缝；内容相对边框内缩时
    位置会偏一些，间隔 < 8pt 或偏离中线 > 15% 会回退中线。逐页结果可能因此尺寸不同——
    要每页尺寸一致就用默认的 `gutter: middle`。
  - `pdf_crop` **只裁不缩**：不改变内容比例与字号；`trim` 的内容边界来自低倍渲染的暗像素包围盒，
    很浅的灰底、细彩线可能不算作内容。
  - `pdf_arrange` **只改顺序与 `/Rotate`，不改几何**：不裁剪、不缩放、不旋转内容本身
    （旋转是写 `/Rotate` 让阅读器去转）。
  - `pdf_merge` 逐文件取页后拼接，保留各页原有页面尺寸与 `/Rotate`，不做统一或缩放。

```sh
# 然后重启 DSH：桌面端退出重开；web 端重启 dsh 进程

# 只有开了 surface: true 才需要关心浏览器侧：
# 改了 public/app.js 不必 build（路由每次请求都从磁盘读，且带 no-store），刷新页面即可
# 默认（surface 未开）时页面根本不加载 app.js，所以看不到浮层是正常的，不是坏了
```

没重启有个现成症状：`curl .../plans` 返回 `401 unauthorized`——这是 DSH 对**未注册**的 `/api/*` 路径的兜底，
说明进程里跑的还是没有 `/plans` 路由的旧包（开了 `surface: true` 的话，浮层卡片区会显示灰字
「计划接口暂不可用」）。

## 为什么是 host-only 架构（浮层默认关闭）
这个插件的主界面是**助手调用工具**：用自然语言说要做什么，Agent 调工具，结果回到会话里。
页面里**默认什么都不出现**——没有右下角入口、没有工作台、也没有卡片。

之所以仍带一份浏览器脚本（`public/app.js`），是因为它**可选**：想给人一个可视化工作台时，
在 profile 的插件配置里设 **`surface: true`**（与 `requireConfirmation` 同一处），
网页端与桌面端就都会出现浮层（右下角「PDF 工作台」入口 + 分析 / 编辑 / 水印 / 预览标签页 +
「待确认操作」卡片）。**确认流程不依赖它**：不注入时确认单以纯文本返回，用户对助手说「确认执行」即可。

浮层没有做成 `dsh.client` 客户端插件，而是由宿主自己的路由提供、必要时注入进页面的普通脚本。
原因是踩过的坑：`dsh.client` 插件要通过 GUI 的客户端模块系统物化，而它声明的 `dsh.client.inject`
要对着**当前运行的那个外壳**的服务图解析。桌面端外壳的服务图和 web 外壳不是同一套 ——
声明了对方没有的服务，插件就会永远停在 `pending (waiting for service)`，功能不出现且不报错。

所以浏览器侧是自带的静态脚本，`surface: true` 时经**两条通道**注入。两条都已真正实现（`src/index.ts`），
并有装配层测试钉住（默认关闭时，行表 0 行、0 个监听器、0 个 `tapIndex`）：

| 通道 | 适用外壳 | 说明 |
|---|---|---|
| `webserver/index-inject`（主） | 桌面 / web | 往宿主给的结构化行表里追加两行：`{kind:'global', name:'__DSH_PDF_STUDIO__'}` 与 `{kind:'script-src'}` |
| `webServer.tapIndex`（兜底） | web | 万一某个宿主不消费行表，就直接改写 `index.html`，在 `</head>` 前插入同一段 boot 与脚本标签 |

两条都注册，各自在不适用的外壳上是空操作。三个容易漏掉、但缺了就"看起来没坏、功能不出现"的性质：

1. **注入的地址是绝对地址。** `apiBase = http://<host>:<port>/api/pdf-studio`、`scriptSrc = http://<host>:<port>/dsh-pdf-studio/app.js`。
   桌面端用 `file://` 加载页面，相对路径在那里没有意义；只有拿不到端口时才回退成相对路径。
   绑定 `0.0.0.0` / `::` 时，浏览器侧一律换成 `127.0.0.1`。
2. **两侧都幂等。** 行表按 `row.name` 去重（同一张表重复广播不会插两次）；`tapIndex` 的 HTML 变换先检查脚本标签是否已存在。
3. **两侧都由浮层再兜一层。** `public/app.js` 用 `window.__dshPdfStudioMounted` 与 `#dsh-pdf-studio-host` 双守卫，
   第二次执行直接返回——否则网页端与桌面端各注入一次就会叠出两个浮层。

注入的全局变量是 `global.__DSH_PDF_STUDIO__ = { apiBase, scriptSrc, requireConfirmation }`，
浮层优先读它、拿不到才回退同源相对路径 `/api/pdf-studio`（`apiBase` 末尾的斜杠会被剥掉，不会拼出 `//plans`）。
监听器在 **root 上下文**与 **webServer 服务上下文**两处都挂（宿主可能把事件发在任一处），重复的靠行表去重兜住。

### ⚠️ 注册顺序陷阱（只在 `surface: true` 时相关）

桌面端宿主的注入表是**启动时一次性收集并缓存**的，没有刷新路径。插件的
`webserver/index-inject` 监听如果晚于那次收集，行就永远进不去，而且**没有任何报错**。

因此 `surface: true` 时监听是**同步**挂上的（不推迟到服务依赖之后）；所有依赖服务的动作放进
`root.inject([...], cb)` 里等待。见 `src/index.ts`。

## 分诊的判据（为什么是三条）
"文字层非空就是数字版"是错的，而且错得很贵。

实测 `demo/source/ceshi.pdf`（6 页扫描件）：**每页都有文字层**，但内容只有一串
防伪指纹 `{#{QQAB…=}#}`，位于 `y=0`、5pt 字号，正文一个字都没有。只看"有没有文字"
会把整份扫描件判成数字版，然后给用户一个空的编辑器。

所以三条一起判：

| 判据 | 作用 |
|---|---|
| 可信字符数 | 排除只有零星字符的页 |
| **位置与字号** | 页边 24pt 带内、≤7pt 的字符视为指纹/水印，不计入正文 |
| 图像覆盖 | 有整页图像 → 扫描件 |

实测判定：`ceshi.pdf` 6/6 → **图片型**（正文占比 0%）；`contract.pdf` → **文本型**（260/260，100%）。

## 可编辑模型：可读的 run
画板要显示的不是字形 ID，而是文字。所以补上了 **ToUnicode 解码**这一层：

| 能力 | 说明 |
|---|---|
| `parseToUnicodeCMap` | 解析 CMap 的 `bfchar` / `bfrange`（含数组式与递增式两种）与 codespace 宽度 |
| `readPageFonts` | 逐字体读取 `ToUnicode`、`/W` 宽度表、`/DW` 默认宽度 |
| `listReadableRuns` | 给出每个 run 的 `id` / **解码文本** / 字体 / 字号 / 基线 / **实测宽度** |
| `readEditableDocument` | 整份文档的可编辑模型（按页组织） |
| `applyTextEdits` | 按同一个 `id` 回写，并**另存新文件**（永不覆盖源） |

真实合同上解码结果（13 个 run 全部可读）：

```
1:6   y=762 size=22 w=106.3pt  "服 务 合 同"
1:16  y=782 size=10 w= 50.0pt  "合同编号："
1:26  y=692 size=11 w=176.0pt  "甲方（委托方）：示例科技有限公司"
1:76  y=560 size=11 w=385.0pt  "四、保密条款：双方对本合同内容负有保密义务，未经对方书面同意不得披露。"
3:6   y=120 size=12 w=228.0pt  "【法务终审】条款审核通过，同意盖章签署"
```

**解码正确性是交叉验证过的**：把整页解码出的字符与 pdf.js 的提取结果逐字符比对 ——
**134 个不同字符完全一致、总数 260/260 一致**。这比抽查某个 run 有力得多，因为
CMap 用错时通常只影响页面上的一部分字体。

**读-改-读 闭环已验证**：

```
读模型 → 取到 run 1:76「四、保密条款…」→ 按该 id 改写 → 重新读取输出
  → 该 run 变为「四、保密条款：…（已由法务修订）。」
  → 其余 12 个 run 文本完全不变
```

（改写后 id 会变，因为新嵌入的子集让算子下标整体前移 —— 这是正确行为，见下方"已知边界"。）

### 溢出预警

替换后用**各自字体的度量**测量宽度并预警，而不是看字符个数 —— 替换字体与原字体的
advance width 通常不同。实测：

```
短替换  → 无提示
超长替换 → "3:6 替换后预计宽约 576.0pt（估算），超过原 228.0pt，可能向右溢出"
```

### 内容流回写（实测）

**改字是可行的，而且是外科手术式的。** 在真实合同上把页脚文字替换掉，验证结果：

| 检验 | 结果 |
|---|---|
| 替换后的文字可被提取 | ✅ 重新打开 PDF 能读到新文本 |
| 原文字消失 | ✅ 旧页脚文本不再出现 |
| 页面其余部分仍正确 | ✅ 标题、编号、正文全部完好 |
| **未改动的内容流逐字节相同** | ✅ 3/3 个流字节级一致 |
| **改动仅限目标算子窗口** | ✅ 窗口前的 head、窗口后的 tail 完全未动 |
| **渲染像素差分** | ✅ 变化全部落在被改文本块内；该块上方**0 个像素变化** |
| 新字体子集已登记 | ✅ `/Resources /Font` 多出 `ArialUnicodeMS` |
| 源文件未被修改 | ✅ SHA256 全程不变 |

编辑后的内容流（对比原文，只动了这一处）：

```
原文: /ArialUnicodeMS-6703682664 12 Tf ... 1 0 0 1 70 120 Tm <0001...0012> Tj
改后: /ArialUnicodeMS 12 Tf <000100020003000400050006000700080009> Tj
      1 0 0 1 70 120 Tm 保持不动 → 基线完全不变
```

**实现要点**（每一条都是踩出来的）：

1. **把整个文本状态窗口当一个 span 替换** —— 从 `Tf` 的字体操作数到最后一个字形串。
   拆成"字体名"和"字形"两个 span 会失败：字体名那个 span 一旦丢失，流就会
   **用旧字体显示新子集的字形 ID**，文字画成乱码、提取为空。
2. **`Tf` 是独立算子**，不在 `Tj` 的操作数里 —— 必须向前扫描找到生效的那一个。
3. **窗口天然包含结尾的 `Tj`** —— 替换文本不能再自带 `Tj`，否则得到 `...> Tj Tj`。
4. **pdf-lib 的 `encodeText()` 返回 `PDFHexString`**，不是 Buffer —— 用 `.length`
   或下标去读会得到 `undefined`，看起来像"没实现"（我为此白查了一轮）。
5. **`/Contents` 是数组时必须换引用，不能改内部** —— 用 `PDFRawStream.of` +
   `context.register` 登记新流，再重建 `/Contents` 数组。

### 内容流回写的关键约束（实测）

1. **页面是多个内容流组成的数组**。`contract.pdf` 的 `/Contents` 有 4 个流
   （`q` / 正文 / `Q` / 尾段），13 个 showText 分布在流 1 与流 3 —— 补丁必须定址到正确的流。
2. **文本是字形 ID，不是字符**。`<0001000200030002000400020005>` 是该字体子集里的
   字形序号；字符含义由字体的 `ToUnicode` CMap 决定。所以解析器**返回原始操作数**，
   绝不假装能解码成字符串。
3. **字体键是按页、且每段文本一个子集**。该页 13 个字体资源全部是同一底座的独立子集，
   **且全部指向同一个 PDF 对象**。改字若要新字形，最稳的做法是**新嵌入一个子集**并
   在资源字典里登记，而不是去改原字体。
4. **pdf-lib 的字形编码只在保存期可用**。`CustomFontSubsetEmbedder.encodeText()` 依赖
   `subset.includeGlyph()` 分配**子集内**的 ID，而 `subset` 在 `embedFont` 之后、保存之前
   并不就绪 —— 直接调用返回空。因此内容流拼接必须放进**保存钩子**里执行，不能提前算好。
5. **无损性是补丁可信的前提**。解析器保证"把 token 拼回去等于原文"，实测 4/4 个真实流
   完全无损；这样"只有目标 span 变化"才是可检验的性质。

### 已修复的真实缺陷（解析器）

分词器早期在遇到**转义括号**时会让扫描位置越过输入末尾（`i += 2` 无边界检查），
外层数组扫描随之失去终止条件，**无限循环并耗尽内存**。已重写为每个分支都保证前进，
并加了 10 个畸形输入（未闭合字符串/字典/数组、游离分隔符、末尾反斜杠）的终止性回归测试。

## 画板：可点选、可改字、可另存
浮层（`surface: true` 时）现在有两个标签页：**分析**（分诊 + 可搜索 PDF）与**编辑**（画板）。

做法：**宿主把页面栅格化成 PNG 做底图**，浏览器侧按每个 run 的 PDF 几何叠加
可点选框。渲染刻意放在宿主侧 —— 浏览器侧就不必配置 pdf.js worker，少一个
环境相关的失败点，并且复用了 OCR 阶段已经验证过的渲染路径。

| 交互 | 行为 |
|---|---|
| 点框 | 选中并打开编辑器，显示 run id / 字体 / 字号 / 基线 / 实测宽度 |
| 改字 → 应用 | 框变绿，底部列出待写改动，可逐条撤销 |
| 另存编辑结果 | 调 `/apply` 写新文件（**永不覆盖源**），返回应用处数与提示 |
| 翻页 / 缩放 | 逐页浏览，滑块缩放；底图按页缓存，不因改字重新拉取 |

### 为什么这块值得测：y 轴翻转

PDF 是**左下原点**，底图是**左上原点**，每个框都要翻转一次：

```
top = (pageHeight - (run.y + height)) * scale
```

符号写反会把所有框**上下镜像** —— 在对称页面上看着正常，在其他任何页面都是错的。
所以测试用 run 自身的真实几何**独立算出期望坐标**再比对，并额外加了一条性质断言：
"高处的 run 必须显示在低处 run 之上"。

实测（`contract.pdf`，底图宽 595px）：

```
标题 run (PDF y=762)  → top =  52.5   期望 52.5
页脚 run (PDF y=120)  → top = 706.6   期望 706.6
且 52 < 707  → 翻转方向正确
```

### UI 是怎么验证的

`public/app.js` 是无依赖、由注入加载的普通脚本，所以测试**真的把它跑起来**：
jsdom 建文档 → 执行该脚本 → 打桩 `fetch` → 走完「选文件 → 载入可编辑内容 →
点框 → 改字 → 另存」，并断言最终 POST 的载荷（目标 run id、新文本、页码）。

这顺带抓到一个**真实体验缺陷**：原先每次改字都重建底图并重读 `clientWidth`，
叠加层会瞬间塌陷、画面跳动。已改为按页缓存底图。

## 密码保护：加密 / 解密
加密**没有自己实现** —— 而是交给 **qpdf 编译成的纯 WASM**（`@jspawn/qpdf-wasm`，
Apache-2.0，零依赖）。密钥派生、owner/user 权限分离、revision 6 哈希都是专业活，
自己写一个"看起来能开"的版本，结果往往是别处打不开、或比宣称的更弱。

| 能力 | API |
|---|---|
| 加密（用户密码 + 所有者密码 + 权限） | `encryptPdf` |
| 解密（凭密码） | `decryptPdf` |
| 查询保护状态 | `inspectEncryption` |
| 端到端（读文件 → 写文件，**不覆盖源**） | `protectPdf` |

实测闭环（`contract.pdf`，AES-256）：

```
原文        → encrypted=false  opens=true
加密后      → encrypted=true   opens=false      ← 独立读取器拒绝提取文字
错误密码    → 拒绝（exit 2）
空密码      → 拒绝
正确密码    → 解密成功 → encrypted=false opens=true
            → pdf.js（独立实现）能读、页码保留、正文完好
```

### 让 qpdf 在 Node 里跑起来

qpdf-wasm 是 Emscripten 浏览器构建：模块作用域就读 `self`/`document`，加载 `.wasm`
走 `fetch`（无法解析裸文件路径），还依赖 `Worker`。解法不是堆 polyfill，而是
**自己编译 wasm 再通过 Emscripten 的 `instantiateWasm` 钩子交进去** ——
模块自带的加载器完全不执行，全程只用本地字节。

### 三个必须记下的"静默错误"

1. **不能从 qpdf 日志判断加密状态。** `--show-encryption` 的报告**走不进**
   Emscripten 的 `print`/`printErr` 钩子（`output` 是空串），基于日志的判断会把
   **已加密的文件报成未加密** —— 对这个功能而言是最坏的失败方向。因此改为结构化判定：
   `/Encrypt` 取自 **trailer**（不是全文搜索，否则正文里的 `/Encrypt` 字样会误报），
   "能否免密打开"由一次真实的零密码读取决定。
2. **`--modify` 只接受一个值。** 逗号列表会被直接拒绝；而权限层级是累积的
   （`form` 已含批注、`assembly` 已含表单），所以多个请求必须**收敛到最高那一级**，
   不能拼接 —— 拼接是最自然的写法，且每次都失败。另外值名是 `assembly` 不是 `assemble`。
3. **模块会污染 `process.exitCode`**（实测被设成 2）。在 CLI 里这是预期行为，
   在长期运行的 DSH 宿主里就是污染 —— 会让整个进程无端以非零码退出。
   已保存/恢复原值。

第 3 条顺带牵出我自己的一个 bug：我一开始把 `process.stdout.write` 换成"吞掉字节"的
函数，**破坏了 Node 自身的错误输出通道**，于是任何 teardown 异常都变成"静默 exit 2、
没有任何信息"，排查了很久。现在改为**观察并转发**（原始 write 照常执行），
`process.stdout` 在 Node 26 上也已不可赋值。

## 水印：加得可靠，删得诚实
### 加水印

水印是**两层 XObject**：

- **内层 mark**（`/WMMark`）只描述"要画什么"——一段字形、一组字形轮廓，或一张图片；
- **外层水印**（`/Name` 里写身份标识），按页面几何把内层 mark 摆到该去的位置。

每一页只新增一条 `Do` 调用（放在一个新内容流里），既有内容一个字节都不改写。
外层按**页面几何**缓存，所以 73 页同尺寸的文档只有一个外层对象；内层只有一份，
因此轮廓模式不会随平铺数线性膨胀。

支持 `tile` / `center` / `corner` 三种位置、旋转、透明度、颜色、字号、边距、图片水印、
按页选择，以及下面两种绘制模式。

#### `render: text | outline`

| 模式 | 画出来是什么 | 文字层 | 是否内嵌字体 |
|---|---|---|---|
| `text`（默认） | 真实字形（`Tj`） | **会被搜索/复制/提取读到** | 是（子集） |
| `outline` | 同样的字形，但是填充路径（贝塞尔） | **完全没有文字** | 否，文件反而更小 |

"内部资料""机密"这类标记通常要的是"看得见、拿不走"，所以用 `outline`：
TrueType 是二次曲线，PDF 只有三次曲线，转换用的是精确升阶
（`c1 = p0 + 2/3(q - p0)`，`c2 = p2 + 2/3(q - p2)`），外观与 `text` 完全一致。

两种模式都会把调用包进 `/Artifact <</Type /Pagination /Subtype /Watermark>> BDC … EMC`：
水印是装饰而不是正文，辅助阅读与 PDF/UA 检查器据此跳过它（`artifact: false` 可关闭）。

#### 平铺不会切掉半个字

平铺网格是**内接**的：先取 mark 自身的**旋转后包围盒**，把它放进页面可见区域
（CropBox，而不是 MediaBox），再把行列**均匀铺满**剩下的空间，奇数行错开半步并少放一个 tile。
因此每个 tile 都完整落在页内，四边不会出现被裁成一半的字形 ——
早期版本从页面外一个 stride 处起铺、靠 Form 的 BBox 裁切，四个边全是被切开的字。

### 删水印：能删到什么程度，取决于它当初怎么被写进去

| 写入方式 | 能否删除 | 原因 |
|---|---|---|
| 页面用 `Do` 调用的 Form XObject | ✅ 精确删除 | 调用就是一个算子，删掉它即删掉整块，且不碰其他内容 |
| 内联在页面流里的算子 | ⚠️ 通常可以，但属启发式 | 它与正文在种类上无法区分，只能靠几何与图形状态判断 |
| 栅格化进页面图片 | ❌ 不能 | 像素就是页面本身，分离它们是图像修复，必然有损 |
| 作者当正文画的 | ❌ 不能 | 那就是正文 |

所以 `scanWatermarks` 返回**带置信度和理由**的候选，`removeWatermarks` 默认
**只删能自证的**（置信度 ≥ 0.9），并且**默认 dry run**。它从不宣称"什么水印都能删"——
那个宣称是假的，而一个"静默删掉一半"的工具比一个"说清为什么不能删"的工具更糟。
无法处理的情况会出现在 `refused` 里，UI 会把它显示出来，避免"空列表"被误读成"这个文件很干净"。

**识别用的五个信号**（`scanWatermarks`，按可靠度排序）：

| # | 信号 | 置信度 | 说明 |
|---|---|---|---|
| 1 | `/Name` 带本插件的 `WATERMARK_MARKER` | 1 | 自己盖的章，确定性识别 |
| 2 | `/PieceInfo /ADBE_CompoundType /Private /Watermark` | 1 | Acrobat 系水印的自述身份 |
| 3 | `/Artifact<</Subtype/Watermark>> … BDC … EMC` 包裹 | 1 | 文件自述这是水印装饰，与算子数量无关 |
| 4 | `/Artifact<</Subtype/Header\|/Footer\|/Pagination>>` 包裹，**且**内容只画文字、`/BBox` ≤ 页面 5%、同一对象跨 ≥ 2 页重复 | **0.7** | 出版站点给讲义盖的"微信搜索：XXX"就是这一种 |
| 5 | 未命名 XObject（常透明度 + 至少一个绘制算子）/ 旋转的内联文字 | 0.45 / 0.35–0.6 | 兜底启发式，需人工判断 |

第 4 条刻意压在默认门槛之下：**真正的页眉页脚带的是同一个 `/Subtype /Header` 标签**，
结构上与这种水印无法区分，所以它只在扫描结果里被单独报出来、默认一个都不删；
用户确认"那就是水印"之后，用 `pdf_watermark action=remove minConfidence=0.7` 显式删。
`minConfidence` 会写进确认单——计划说 0.9、执行却按 0.7 删，等于用户确认了另一件事。

`refused` 同样做到"看到了就说"：一个 artifact 对象被看见、但判定不是水印时（面积超标、
含几何算子、没有跨页重复），每一页都会写明**具体哪一条判据不满足**，而不是笼统地说
"没找到水印"再无下文。

删除时会连**外层的 `/Artifact … BDC … EMC` 包裹一起删掉**：否则每页会留下一个空的
artifact 块，日后扫描看起来像"有标记内容"，人只能靠猜。传进来的候选列表还必须
能**在本次扫描里对上号**，不匹配（列出的是别的文件、或已过期）的候选一律忽略 ——
候选里只是一串资源名，照着删会删掉本文件里恰好同名的东西。

### 添加水印时踩到的坑（都会导致"水印隐形"或"文件变大"）

1. **必须写字体编码后的字形串，不能写原文字。** 子集字体会重新编号字形，
   直接写 `(内部资料) Tj` 画出来的是"恰好落在那些码位上的字形"，也就是乱码或空白。
   必须用 `font.encodeText(text)` 的结果作为操作数。
2. **XObject 的 `/Resources` 必须指向真实对象。** 我一开始写成空字典占位
   （`{ [fontRef]: {} }`），于是 `Do`/`Tf` 解析到空对象，**整个水印画出来是空的** ——
   文件里结构齐全、扫描器也认得，但页面上什么都没有。这个坑只有渲染出来看才能发现，
   所以"渲染像素差分"是这套测试里最有价值的一条。
3. **图片水印的引用被 `void ref` 丢掉了。** 同一个坑的图片版本：图片对象注册了，却没人
   引用它，页面照样"成功"，只是空白。内层 mark 的 `/Resources` 现在显式带上图片引用。
4. **不要用 `page.node.Contents()` 拼新数组。** 它会把间接引用解析成对象，于是新数组里
   直接内联了一份正文内容（内联流），原来那个流对象变成孤立对象 —— 正文被存了两份，
   6.7MB 的文档每加一次水印就 +349KB。要用 `page.node.get(...)` 保留引用。

## 预览：打开就能看到文档
浮层（`surface: true` 时）第一个标签页就是**预览**。选好文件点「打开预览」，所有页面以缩略图铺开，
点任意一页放大到全屏。

| 细节 | 做法与原因 |
|---|---|
| 页面几何从 `/info` 取，**不走** `/analyze` | 分析会对扫描件跑 OCR（每页数秒）。为了看第 1 页而等 OCR 是不可接受的。`/info` 只读页面尺寸，扫描件 6 页 **10ms** |
| 缩略图 `loading="lazy"` | 200 页的文档只加载滚动到的那些页 |
| 缩略图尺寸自适应 | 按页面 pt 宽 × 目标 CSS 宽算缩放比，不是写死倍数 |

### 这里修掉两个真 bug

**① 懒加载与 `display:none` 死锁（就是它导致你只看到"第 1 页"）**

第一版我这样写：

```js
img.loading = 'lazy'
img.style.display = 'none'          // 加载完成前隐藏
img.addEventListener('load', reveal) // 加载后显示
```

这是一个**死锁**：`display:none` 的图片没有布局盒 → 浏览器认为它永远不在视口内 →
**永远不发起请求** → `load` 永不触发 → 永远保持隐藏。用户看到的是一格格
"第 N 页"占位符，而不是文档。

修法：图片**始终参与布局并可见**，占位符作为**绝对定位的浮层盖在它上面**，
加载完成后移除占位符。图片再也不会被隐藏。

之所以没被测试抓到：**jsdom 不实现懒加载**，`img.src` 设上就是设上，`complete` 逻辑
根本不起作用。现在补了一条直接针对该条件的断言：**缩略图不得为 `display:none`**。
我把旧代码改回去验证过，这条断言会 FAIL。

**② 状态行被覆盖**

`renderPages` 会把"N / M 页已显示，K 页失败"写进状态行，但调用方在它之后又写了
一次，把计数冲掉了。改成先写摘要、再渲染。

### 这里修掉一个真 bug

我第一版把 `<img>` 先建好、**加载完成才插入 DOM**。看起来没问题，实际上
**`loading="lazy"` 完全失效** —— 浏览器只观察文档里的元素，游离的 `<img>` 根本不被观察，
于是长文档会一次性拉取所有页。现在图片立即入 DOM 并先隐藏，加载完成后显示，
懒加载才真正生效。

### 顺带修好渲染保真度

预览要**渲染**页面，这让一个之前的判断过期了。`src/core/pdf.ts` 里原本写着：

> 缺少标准字体只影响渲染保真度，绝不影响本管线读取的文本层

在只做文本抽取时这是对的；但预览和画板现在都要渲染，字体缺失是**看得见**的。
于是接上了 pdfjs 自带的两套资源：

- `standard_fonts` —— 未内嵌的 14 种标准字体
- `cmaps` —— 预定义 CJK 编码（中文文档尤其相关）

实测非内嵌 Helvetica 的渲染：字节 11520 → 12526、深色像素 3661 → 3728，
且 pdf.js 的 `standardFontDataUrl` 警告**从 2 条降到 0 条**。

找这两个目录时我先写错了层级（`standard_fonts` 在包根目录，而入口嵌在下面两层），
导致指向一个不存在的路径且**静默无效**。现在改成从入口向上逐级查找。

### 已知边界


- **改写后 run 的 id 会整体前移**（例：`1:76` → `1:74`）。id 是"流下标:算子下标"，
  而插入新字体资源会让后续算子下标变化。因此**一次编辑要用同一份模型里的 id**，
  跨编辑不要缓存 id —— 每次改完重新读模型。
- **0/N 处改写不算成功。** 一处都没应用时 `pdf_edit_text` 不再回"已生成"，而是**明确失败**并说明下一步
  （`applyTextEdits` 在这种情况下**不写盘**，返回值多了 `written: boolean`）：多半是 `targetId` 已过期
  （需 `pdf_inspect runs=true` 重读），或者这一页是图片页、没有文字层（需先 `pdf_make_searchable`）。
  "什么都没改却说已生成"是最危险的假成功，所以这里刻意报错。
- 溢出预警是**估算**：新嵌入的子集在写盘前没有自己的 `/W`，按字体默认宽度计。
  提示文案里已标明"估算"。
- 尚未处理：跨视觉行的整段重排、字距微调（`TJ` 的数值调整）、自动换行。
  （`pdf_replace_line` 已经能重排**同一视觉行**上的多个绘制组，见上文「整行重绘」。）

## 浮层可以拖到屏幕任意位置（可选，`surface: true`）
工作台浮层和右下角按钮都**可拖动**，并且**记住位置**：

| 操作 | 行为 |
|---|---|
| 拖标题栏 / 拖浮层头部空白处 | 移动浮层到任意位置 |
| 拖右下角按钮 | 移动按钮本身 |
| **双击标题栏（或按钮）** | 一键复位到默认右下角 |
| 关闭再打开 / 刷新页面 | 回到你上次放的位置 |

### 两个必须处理的细节

1. **位置要裁剪在视口内。** 存了绝对坐标却不裁剪，窗口一旦变小，浮层就永久跑到屏幕外——
   除了清站点存储没有别的办法弄回来。所以在**加载时和每次 resize 时**都会裁剪，
   保证至少 72×32px 留在可见区域内。
2. **按钮既能拖、又能点开浮层，两者必须区分。** 用移动距离阈值（3px）+ 捕获阶段
   的 click 抑制：拖动不会顺带把浮层弹出来，纯点击照常打开。这条如果做错，
   *每次想挪动按钮都会弹出浮层*，功能会显得完全坏掉。

### 排除规则踩的坑

我第一版把"排除按钮"写成 `event.target.closest('button, input, select, .tab')` ——
但**浮动按钮自己就是 `<button>`**，于是匹配到自身、直接 return，按钮根本拖不动。
测试立刻抓到了。正确写法是先判断 `event.target !== handle`，只排除**手柄内部的**控件。
（浮层头部同时是拖拽手柄，所以这条判断对两处都必要。）

### 实测（jsdom 里跑真实脚本）

jsdom 的 `getBoundingClientRect()` 返回全 0，这让拖拽数学变成**确定性的**：
抓取偏移就等于指针位置，所以指针移到 (clientX, clientY) 后，浮层应精确落在差值处。

```
拖头部 (100,100) → (160,140)  =>  left=60px top=40px      ✓ 精确等于差值
right/bottom 锚定切换为 auto                              ✓
位置写入 localStorage                                      ✓
拖出边界 (99999,99999)        =>  裁剪到 952px (=1024-72)  ✓ 仍在可抓取范围
双击标题                       =>  复位到 right:18px，并清除存储  ✓
拖按钮                         =>  浮层未被打开            ✓ 点击被抑制
纯点击按钮                     =>  浮层打开                ✓
```

## 依赖库的坑（都付过代价）
这些**都是静默失败**，所以记在 `contracts.ts` 里：

1. **`pdf-lib@1.17.1` 的 `drawText()` 没有 `renderingMode` 选项** —— 传了会被忽略，
   隐形层会变成**盖在扫描件上的可见黑字**。必须手写算子
   （`page.pushOperators(...setTextRenderingMode(3))`）。
2. **`pdfjs-dist@6.2.108` 没有 `doc.destroy()`** —— teardown 走
   `loadingTask.destroy()`。`destroy?.()` 会静默变成空操作、泄漏 worker。
   `openPdf` 已把它统一成 `PdfDoc.dispose()`。
3. **`tesseract.js` 在 Node 下必须用 node 版 worker**，否则
   `r.g.addEventListener is not a function`；且 **`blocks` 默认 `false`** ——
   不开就没有任何坐标。
4. **`fontkit@2.x` 与 `pdf-lib@1.17.1` 不兼容**（`encodeStream()`→`encode()`），
   且 macOS 中文字体**全是 `.ttc`**，`fontkit.create()` 返回的是集合而非字体。
   已在模块内做适配。
5. **字体资源键是按页声明的**。按"字体"缓存会让第二页的 `/Font` 字典为空 ——
   文字照常渲染，但提取出来是裸字形码，于是"可搜索 PDF"其实搜不到。
6. **pdf.js 的文本 transform 已经是 PDF 坐标，不要翻转** ——
   全页 13 项实测：按 PDF 解读命中 397 墨点，按设备坐标解读命中 0。
